### N2（正确性 · 潜伏）同步/异步并轨只做了一半

`_run_sync` 明确处理了「已存在运行中的 event loop」，但 `_iterate_sync` **没有**。
两者对同一场景的行为不对称——实测（`var/probe_review_sync_bridge.py`）：

```text
A. _run_sync 嵌套调用          : OK -> 'T'
B. _iterate_sync 嵌套调用      : FAIL RuntimeError: Cannot run the event loop while another loop is running
C. client.stream() 构造调用    : OK（未迭代，未触发）
C. 首次 next()                 : FAIL RuntimeError: Cannot run the event loop while another loop is running
```

三点值得记：

1. **炸点在生成器第一次迭代**，不是构造时——与 `docs/10` 缺陷 B（`/stream` 的 200 已提交
   才抛异常）是同一型故障；`client.stream()` 会先返回一个生成器，异常延迟到调用方 `for` 时才出现。
2. **当前是潜伏的**：全仓唯一的同步 `stream()` 调用点是 `run_client.py:64`，在模块顶层执行、
   没有运行中的 loop；`streamlit_app.py` 走的是 `astream`。所以今天不会炸。
3. **但它正是 batch 5 声称达成的目标**：`_run_sync` 的 docstring 写着「检测到运行中的 loop 就退到
   工作线程」，而并轨的收益正是「同步 API 在 async 上下文里可用」。HEAD 新增的 3 条用例
   （`test_sync_bridge_propagates_error` / `test_sync_stream_propagates_error` /
   `test_sync_call_inside_running_loop`）**全部只覆盖 `_run_sync`**，`_iterate_sync` 的嵌套分支零覆盖。

| 修法（二选一，都不动公开签名） | 说明 |
| --- | --- |
| 在 `_iterate_sync` 里做同样的探测 | 有运行中的 loop 时，把整个迭代放到一个工作线程上驱动；注意生成器要跨线程 yield，需用 `queue.Queue` 或 `asyncio.run_coroutine_threadsafe` 桥接 |
| 给 `stream()` 补同样的入口分派 | 无 loop 时保持现状（当前唯一调用路径），有 loop 时委托到线程版迭代 |

**验收建议**（判据必须能真的失败）：仿 `test_sync_call_inside_running_loop`，加一条
`async def test_sync_stream_inside_running_loop`，断言 `list(agent_client.stream("q")) == ["tok"]`；
去掉修法后必须变红（现状实测就是 `RuntimeError`）。
