## 2 A 组：会误导实施，建议先改

### A1 §2.8 的回归用例与 §2.3 的结论直接冲突

§2.3 推论 1 明确写了：E3 成功时 `adjacent_assistant=1`，**相邻 assistant 消息与成功可以共存**，
先前那套「连续 assistant 触发校验」的说法是错的。

但 §2.8 的测试表里仍保留一条：

> 消息序列无相邻 assistant ｜ 断言 `-1` 步产物 ｜ 防止 `full_history` 形态回归

这条用例**没有对应的失败机理**——真实触发条件（缺 `reasoning_content`）与消息是否相邻无关。
结果是：它跑绿了拦不住任何真实回归，却把已被证伪的假设固化进了测试，
下一个人会照着它去理解成因。

**改法**：断言换成真实条件，或退回到行为断言。

| 现在 | 建议 |
|---|---|
| 断言「无相邻 assistant」 | 断言「出站消息里不存在缺少 `reasoning_content` 的 assistant 消息」 |
| 或 | 直接断言「转交链路返回 200 且最终答案正确」（行为级，不锁实现） |

### A2 §2.3 的结论强度超过证据

§2.3 写「触发条件已由 E3 反证钉死」「原计划的 E5 不再需要」。但回看证据：

| 实验 | 实际证明了什么 |
|---|---|
| E1 / E2 | **只否证了**「编排配置是触发条件」这一个假设 |
| E3 | **只证明了**「关掉 thinking → 200」 |
| E5（已取消） | 唯一能**正向识别**触发字段的实验 |

E1/E2/E3 都**没有观测过失败请求的载荷**。所以「历史里存在非本模型生成的
content-only assistant 消息」这个正向判断，性质是**推断**，不是实测结论。

方案自身也承认这一点：§2.4 把路线 C 标为「未验证」，§2.6 留了一个「待决点」。
三处口径（钉死 / 未验证 / 待决）互不一致。

这不是文字问题——**路线 C 的全部设计前提就是这个识别**。方案等于在
「前提未验证」的状态下推荐了一条需要新写一整张图的路。

**改法**（低成本、直接决定 C 与 D 能不能成立）：不构建图，直接用 SDK 构造两组历史
各调一次带 `tools` 的请求——

| 组 | 历史形态 | 预期 |
|---|---|---|
| C1 | 子 Agent 终答作为 `AIMessage` 放入历史 | 400（与现象一致） |
| C2 | 同一条终答改为 `ToolMessage` 放入历史 | 200 → **路线 C / D 的前提成立** |

这比已取消的 E5（逐字段 diff）便宜得多，而且结论直接可用。**在跑完它之前，
不该把路线 C 当成已定方案；跑完之后，§2.3 的措辞也可以从「钉死」改成有依据的结论。**

### A3 §2.7 第一条是误诊

方案把这条列为**高优先级缺陷**：

> `workflow(chosen_model)` 参数化了，调用点传的是全局 `model` —— 改到一半没接上
> （`hierarchy:10 / :46`）

回代码核实：`workflow(chosen_model)` 内部**三处全部**用的是 `chosen_model`
（`:13` 数学子 agent、`:21` 内层 supervisor、`:35` 外层 supervisor）。参数是完整接通的。

而调用点 `:46 workflow(model)` 传模块级 `model`，是 import 期**唯一可行**的做法——
图在 import 期就编译，运行时根本不存在「用户选中的模型」。方案自己在 §2.2 第一条
承认了这一点。

所以这不是「接了一半」，最多是「参数只有一个调用点」。而且方案没写出
「修完之后应该是什么样」，这条**无法验收**。

**改法**：降级为「与 `langgraph_supervisor_agent.py` 的风格统一」，或直接删除。

### A4 §2.7 第二条把 `web_search` 的归属写错了

原文：

> 三级转发导入 `web_search`（**实际定义在 `research_assistant.py`**）｜改为 `from agents.tools import web_search`

核实：`web_search` **只定义在 `src/agents/tools.py:77`**。
`research_assistant.py:14` 与 `langgraph_supervisor_agent.py:6` 都只是**再导出**（跨 agent 模块借用）。

方案 §1.1 自己写的是 `agents/tools.py:47-74`，两处**自相矛盾**。

**改法**：改动方向（`from agents.tools import ...`）是对的，但理由要改对——
问题是「借道兄弟 agent 模块」，不是「定义在别处」。

### A5 漏掉一条库内自带的中间档路线（路线 D）

方案把「保住 thinking」的代价默认成了「自建整张 supervisor 图」（路线 C），
于是路线对比退化成了「A：不要 thinking」对「C：重写编排」。

但 `langgraph_supervisor` 0.0.31 的签名里就有 `pre_model_hook`
（`supervisor.py:220`，`:438` 透传给 agent 工厂），而它支持返回
`{"llm_input_messages": [...]}` **只改这一次送给 LLM 的消息**，不改图状态
（`langgraph/prebuilt/chat_agent_executor.py:639` 消费）。

因此存在一条方案没评估的路：

> **保持 `langgraph_supervisor` 不动，用 `pre_model_hook` 在出站前把
> 「缺少 `reasoning_content` 的 content-only assistant 消息」改写成 `ToolMessage`。**

它与路线 C 在语义上完全等价（子 Agent 终答以工具结果形式回到 supervisor），
但改动量约 10 行，且 §2.6 列的三条 UI 契约**一条都不用碰**——交接工具命名、
`skip_stream` 约定、子 agent 状态是否入主图，全部沿用库的行为。

这不是新推理出来的结论：日志 `.workbuddy/memory/2026-09-17.md:629-637` 已记录了
决定性的官方规则——「请求携带 `tools` 时，**所有历史轮次**的 `reasoning_content` 都应传回」，
`.workbuddy/tools/probe_fix.py` 的 docstring 也是照这句写的。
**方案正文没有引用这条规则，因此也就没能从它推出路线 D。**

补上之后，路线表的取舍会变清楚：

| 路线 | thinking | 改动量 | 验证状态 |
|---|---|---|---|
| A | 丢 | 极小（配置） | 已验证 ✅ |
| **D（新）** | **保** | **小（约 10 行 hook）** | 未验证，可用 A2 的实验定档 |
| C | 保 | 大（自建图 + 三条契约） | 未验证 |

建议：**A2 实验跑完后先试 D；D 不通再上 C。** 方案原文「A 止血、C 演进」
这个二选一，中间少了一档。

## 3 B 组：方案不完整

### B1 一条验收标准没有对应的执行步骤

§0 验收口径第 1 条要求「转交场景**在 UI 上走通**（含 `transfer_to` 展示）」，
但 §3 执行顺序里没有任何一步覆盖 UI 端到端——步骤 5 的产出只写「转交返回 200」。

**改法**：要么在 §3 补一步（起 streamlit，人工走一遍转交 + 嵌套转交），
要么把该验收降级为「服务端 200」并写明 UI 验证另行安排。

### B2 路线 A 的最大风险没有测试守住

§2.5 自己警告了 `get_model` 的 `@cache` 可能被污染，但 §2.8 的测试清单里
**没有任何一条守住它**。而这正是 4 行改动里最容易悄悄伤到其余 10 个 agent 的地方。

**补一条**：断言 supervisor 使用的 model **不是** `get_model(settings.DEFAULT_MODEL)`
返回的那个对象，且后者的配置未被改动。

### B3 §2.5 的实施机制含糊

原文「在 supervisor 模块里基于 `get_model(...)` 再构造」——但 `get_model(model_name, /)`
是**位置参数 + `@cache`**，签名上就塞不进新参数，读的人会各自发挥。

**建议直接把机制写死**（pydantic 拷贝，不触碰缓存里的原实例）：

```python
base = get_model(settings.DEFAULT_MODEL)
model = base.model_copy(update={"extra_body": {"thinking": {"type": "disabled"}}})
```

### B4 `fetch_url` 的 `max_chars` 由模型可控

§1.3 把上限设计成工具参数 `max_chars: int = 4000`，同一节又写「体积上限**不能省**」。
两者抵触：模型完全可以传 `max_chars=100000` 把上下文撑爆。

**改法**：代码里写死硬上限，参数只允许在硬上限内收窄（`min(max_chars, HARD_CAP)`）。

### B5 SSRF 测试缺了最关键的一条

现有 7 条用例全是「直接输入内网地址」。但实现是「手工逐跳跟随重定向、每跳重新校验」，
那么真正容易写错的是**公网 URL 302 到内网**这条路径——恰恰没有用例。

**补一条**：mock 一个公网 URL 返回 302 → `http://169.254.169.254/latest/meta-data/`，
断言被拦截且**不发出第二次请求**。

### B6 `fetch_url` 只给 loop-agent，与 §1.1 的定性不一致

§1.1 把 P2 定性为**通用能力缺口**（「摘要里根本不含版本号」），而答对 `1.2.11` 的
是 research-assistant。§1.3 / §1.5 却只给 loop-agent 加工具。

方案一边在 1.2 强调「两处副本正是这次漏改的成因」，一边在 1.3 制造新的工具集不对称。

**改法**：明确写 research-assistant 是否同加；若不加，写明理由。

### B7 方案未收录「伪值注入已证伪」这条既有证据

`.workbuddy/tools/probe_fix.py` 记录过一次尝试：向出站载荷注入
`reasoning_content=""` 与 `"placeholder"` **都返回 400**（注入确实生效，但伪值被拒）。

这条否掉了「补一个空字段就完事」的直觉方案。不写进方案，读者很可能会重新提出它。
建议并入 §2.3 或 §4「本方案不做的事」。
