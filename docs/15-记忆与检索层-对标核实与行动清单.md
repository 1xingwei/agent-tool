## 0. 一句话结论

本项目**记忆层已经踩在行业共识上**（checkpointer / store 双层分离），但只用了共识的骨架，没上肌肉；
**检索层还停在 2023 年的朴素 RAG 形态**（固定切块 + 纯向量 + k=5 + 无重排 + 无评测），
而 2026 年企业级检索的及格线是**混合检索 + 重排 + metadata + 评测闭环**四件套。

有意思的是：连 Mem0 这种「记忆层」产品，都已经在检索路径上内置了 BM25 稀疏向量和 reranker，
说明**记忆与检索在 2026 年正在融合成同一层能力** —— 这正是本次重设计的核心判断。

## 2. 记忆层：四种流派，一个共识

### 2.1 四种流派

| 流派 | 代表 | 核心抽象 | 存储 | 谁来决定记什么 |
|---|---|---|---|---|
| 原语派 | **LangMem** | Store 上的 extract / search / optimize 三个功能原语 | 宿主决定（InMemory / SQLite / Postgres+pgvector / Redis） | 框架用 LLM 抽取管道 |
| 抽取管道派 | **Mem0** | `add()` 里 LLM 抽候选事实，再与既有记忆比对决定 ADD/UPDATE/DELETE/NOOP | 向量库（Qdrant 等）+ KV | 系统自动 |
| 操作系统派 | **Letta (MemGPT)** | Core Memory（相当于内存）/ Recall / Archival（相当于磁盘） | Postgres | **Agent 自己**通过工具调用管理 |
| 时序图谱派 | **Zep / Graphiti** | 双时间戳知识图谱：事实带生效区间，被推翻是「失效」而非删除 | Neo4j | 系统自动，保留可审计历史 |

**选型口诀**：Mem0 对你的应用侵入最小、Letta 要求你接受它的运行时、
Zep 给你可审计历史但要自己运维图数据库、LangMem 是「你已经在 LangGraph 上」的默认答案。

### 2.2 共识一：短期记忆与长期记忆是两套东西

LangGraph 官方把这件事定死了：

| | Checkpointer | Store |
|---|---|---|
| 存什么 | 图状态快照 | 应用自定义 KV |
| 作用域 | 单个 thread | 跨 thread |
| 记忆类型 | 短期、线程内 | 长期、跨会话 |
| 用途 | 会话连续性、HITL、时间旅行、容错 | 用户偏好、事实、共享知识 |
| 访问方式 | config 传 thread_id | 节点内读写 items |

**本项目已经对齐这一点**：`src/memory/__init__.py` 里 `initialize_database()` /
`initialize_store()` 两个函数分开，是正确的骨架。

补充一条官方给的容量经验：**state 里不要塞文档正文**。有团队把原始 LLM 响应（含 usage metadata）
塞进 state，50 篇文档时单个 checkpoint 涨到 180KB，Postgres 写入拉到 400ms 并影响响应时间。
正确做法：state 里只放 `document_ids`，正文在节点内按需从存储层取。
这条本项目目前没有违反，但改造检索时容易踩。

### 2.3 共识二：写入是「抽取 + 冲突消解」，不是 append

这是记忆层与「存聊天记录」的分水岭。

**LangMem 的做法**（`var/research/repos/langmem/src/langmem/knowledge/extraction.py`）：

- `MemoryManager` 接收 `{"messages": [...], "existing": [...]}`。
- 把 existing 一起喂给模型，要求它**在同一批并行工具调用里**完成新增 / 修正 / 删除：
  `"If an existing memory is incorrect or outdated, update it based on the new information."`
- 三个开关：`enable_inserts` / `enable_updates` / `enable_deletes`（默认 deletes=False，保守）。
- `max_steps > 1` 时进入多轮迭代：注入 `Done` 工具让模型主动收手，避免无限循环。
- 提示词里明确要求优先保留**反常的**（偏离模式的）和**反复出现的**（被强化的）信息，
  做到不漏记、不误记，宁要密度高的完整记忆，不要互相重叠的碎片。

**Mem0 的做法**：两阶段——先抽取候选事实，再逐条与既有记忆做向量比对，
输出 ADD / UPDATE / DELETE / NOOP 四选一。

两者殊途同归：**写入口不是 append，而是一个带冲突消解的 upsert 决策过程。**

### 2.4 共识三：检索必须混合排序——记忆层也一样

这是本次调研最值得本项目注意的发现。

`var/research/repos/mem0/mem0/utils/scoring.py` 里，Mem0 的记忆检索打分是**三路相加**：

```text
combined = (semantic + bm25 + entity_boost) / max_possible
```

- `bm25`：关键词分数，用 logistic sigmoid 归一化到 [0,1]，且**中点与陡度按 query 词数自适应**（≤3 词用 5.0/0.7，>15 词用 12.0/0.5）。
- `entity_boost`：实体链接加成，权重常量 `ENTITY_BOOST_WEIGHT = 0.5`。
- `max_possible` 按实际启用的信号动态取 1.0 / 1.5 / 2.0 / 2.5。
- **阈值先于融合**：`semantic_score < threshold` 直接出局，BM25 也救不回来——避免关键词撞上来的噪声。

底层存储也配合改了：Qdrant 的 collection 里专门开了一个名为 `bm25` 的 sparse vector 槽位
（`mem0/vector_stores/qdrant.py`），写入时用 fastembed 的 `Qdrant/bm25` 批量编码；
老 collection 没有这个槽位就自动降级、只记一条 warning 继续跑。
查询侧还有 `lemmatize_for_bm25()` 做词形还原。

`mem0/memory/main.py` 的 `search()` 签名也说明了行业默认参数：
`top_k=20`、`threshold=0.1`、`rerank=False`（可选）、`explain=False`（可选返回每路分数明细）。

> 对本项目的含义：**我们的检索工具只有「向量 k=5」，连记忆层产品的起点都不到。**

### 2.5 共识四：Namespace 是有模板的

LangMem 与 LangGraph 的 KV 命名空间统一长这样：

```python
namespace=("memories", "{langgraph_user_id}")
```

大括号里的占位符在运行时从 `config["configurable"]` 取值填充。
同一套代码通过换 namespace 就实现了多用户 / 多团队隔离：

```python
config = {"configurable": {"langgraph_user_id": "user-123"}}   # -> ("memories", "user-123")
config = {"configurable": {"langgraph_user_id": "team-x"}}     # -> ("memories", "team-x")
```

### 2.6 共识五：Store 的语义检索要显式打开，还有 TTL

这是很容易漏的官方行为：

**（1）语义检索默认关闭。** 必须在构造 store 时传 `index`：

```python
store = InMemoryStore(index={
    "dims": 1536,
    "embed": "openai:text-embedding-3-small",
    "fields": ["food_preference", "$"],   # 指定要嵌入哪些字段，默认 "$" 为整个对象
})
```

> 官方原话：*Semantic search is disabled by default. Without this configuration, all index arguments passed to put or aput will have no effect.*

也就是说：**不传 `index`，`put()` 时就算传了 `index=[...]` 也会被静默忽略**，
`search(query=...)` 也拿不到语义排序。

**（2）Postgres 后端就是 pgvector。** `AsyncPostgresStore` 通过 pgvector 做相似检索，
向量单独存 `store_vectors` 表，用 `(prefix, key)` 外键关联并 `ON DELETE CASCADE`；
支持 `hnsw` / `ivfflat` / `flat` 三种索引，向量类型可选 `halfvec` 省内存；
支持连接池 `PoolConfig(min_size, max_size)`。官方 API 里可以直接把 embedding 模型传进去：

```python
AsyncPostgresStore.from_conn_string(
    conn_string,
    index={"dims": 1536, "embed": init_embeddings("openai:text-embedding-3-small"), "fields": ["text"]},
)
```

**（3）TTL 是一等公民。** 写入时可传 `ttl`（分钟）；读取时 `refresh_ttl=True` 会把过期计时器重置。
Postgres 实现用 `expires_at` + `ttl_minutes` 两列，并提供一个后台清理任务——
**必须显式调用 `start_ttl_sweeper()` 才会开始清理**，停的时候 `stop_ttl_sweeper()`。

**（4）抽取与检索可以用两个模型。** LangMem 的
`create_memory_store_manager(query_model=..., query_limit=5)` 允许用一个**更小更快的模型**
专门生成检索 query，主模型负责抽取。生成出来的多个 query 并行 `asearch`，再按 score 合并去重取 top。

## 3. 检索层：企业级七件套

### 3.1 七件套

2026 年企业级 RAG 的标准层次（多家文档口径一致，只是措辞不同）：

| # | 环节 | 朴素做法 | 企业级做法 |
|---|---|---|---|
| 1 | 解析 | 直接抽文本 | 版面分析（表格/多栏/扫描件/公式），表格与正文分流 |
| 2 | 切分 | 固定长度 + overlap | 递归 → 语义切分 → **父子切片** |
| 3 | 索引 | 只有 dense 向量 | dense + sparse **同引擎**，或向量+全文数据库 |
| 4 | 检索 | 纯向量 top-k | **混合检索**（向量 + BM25）+ RRF/加权融合 |
| 5 | 重排 | 无 | **cross-encoder 重排**，召回 20-50 → 重排取 5 |
| 6 | 生成 | 直接拼上下文 | 强制引用来源、上下文不足时拒答 |
| 7 | 评测 | 无 | golden set + RAGAS 四指标 + CI 门禁 |

### 3.2 切分：为什么「父子切片」是标配

朴素固定切块会在两处静默失效：

- 语义断裂——把主语和谓语切开，检索到 `"it was approved"` 却不知道「什么被批准了」。
- 表格被拍平成字符串——行列关系消失，问「Q3 营收差异」时模型只能编。

**父子切片（Parent-Child / Parent-Document Retrieval）** 是当前最实用的折中：
用小切片（如 150 字）做向量匹配以保证命中精度，命中后**回取它所属的大切片**
（如 800 字的完整章节）交给模型以保证上下文完整。

### 3.3 向量库选型：按规模分层，不按 benchmark 选

| 规模 | 选型 | 依据 |
|---|---|---|
| < 10 万向量 / 原型 | Chroma | 零配置、嵌入式，`pip install` 就能跑 |
| < 100 万 | Chroma 或 pgvector | 简单优先，Chroma 单机舒适区到低百万 |
| 已有 PostgreSQL | **pgvector** | 零新增组件；**混合检索一条 SQL 搞定**（FTS + 向量同库同快照）；向量与业务数据事务一致 |
| 10 万 ~ 500 万 | Qdrant | 过滤型 HNSW + payload 索引，专为按租户/日期过滤的查询设计 |
| 500 万 ~ 1 亿 | Qdrant / Weaviate | 分片 + 量化 |
| 1 亿+ | Milvus / Zilliz | 云原生存算分离 |

1M × 768 维 HNSW 实测参考（同一台 8vCPU/16GB 机器）：

| | pgvector | Qdrant | Chroma |
|---|---|---|---|
| 建索引 | 22 min | 5 min | 14 min |
| p50 | 8 ms | 3 ms | 12 ms |
| p99 | 35 ms | 11 ms | 45 ms |
| Recall@10 | 0.95 | 0.99 | 0.94 |

**Chroma 的官方定位就是「原型与本地开发」，没有分布式、没有鉴权。**
有明确说法：Chroma 的 substring matching **不是真正的词法排序** —— 所以想上混合检索，Chroma 不是终点。

### 3.4 云厂商的形态：检索被独立成服务

这是值得本项目架构借鉴的一点。

**AWS Bedrock Knowledge Bases**：全托管 RAG，自动从 S3/Confluence/Salesforce/SharePoint/爬虫取数；
分块支持**固定 / 语义 / 分层**三种，还能挂 Lambda 自定义分块；
向量存储可选 Aurora、OpenSearch Serverless、Neptune Analytics、MongoDB、Pinecone、Redis、
**以及 Kendra 混合检索索引**；内置 **reranker**；所有检索结果**附引用**；
结构化数据走 **NL2SQL** 而不搬数据。

**Azure Foundry IQ**：把检索显式设计成一个**独立服务**，通过 MCP 端点暴露给任意兼容 agent，
返回三样东西——content、references、retrieval activity。文档里那句设计意图很关键：

> *分离「找证据」和「生成答案」。支持助手和入职助手可以用同一个检索服务，不共享指令、对话历史或职责。*

并且明确要求：**检索结果要能区分「没找到」和「找到了」**，不能让调用方从一段看起来合理的文字里猜。

### 3.5 国内开源三强

| | 解析 | 检索 | 评测 | 定位 |
|---|---|---|---|---|
| **RAGFlow** | DeepDoc（版面分析 + OCR，表格/多栏/扫描件强） | **强制混合检索 + 重排**，可视化块管理人工纠偏 | — | 精度极客，复杂文档断层领先 |
| **FastGPT** | auto-QA 分割：LLM 把文档转成问答对再向量化 | **粗排 → 精排 → 重排** 三层 | **内置 RAGAS**，实时生成检索质量报告 | 企业 FAQ / 客服 |
| **Dify** | 固定长度 / 语义分割 | 混合检索 + LLM rerank，底层可换 pgvector / Weaviate / ES | — | 全栈 LLMOps |

三家都在做的事：**混合检索 + 重排**。这已经不是加分项，是入场券。

### 3.6 评测闭环

RAGAS 四指标把「检索」和「生成」两个失败面拆开：

| 指标 | 回答的问题 | 需要 ground truth | 诊断哪一层 |
|---|---|---|---|
| Context Precision | 检索回来的块里有多少真相关 | 否 | 检索 |
| Context Recall | 该找的找到了吗 | 是 | 检索 |
| Faithfulness | 答案有没有超出上下文（幻觉） | 否 | 生成 |
| Answer Relevancy | 答案是否真的回答了问题 | 否 | 生成 |

规模经验：**30 条可看出方向性变化；100 条可信；几百条才能按 query 类型切片定位弱点。**

一个必须知道的局限：Faithfulness 高 ≠ 答案对。**一份过时的文档被忠实地总结，
会同时做到「完全有依据」和「完全错误」**。所以还需要针对本领域加自定义 judge
（比如校验数字准确性、是否标注了来源时效），并且要测「LLM judge 与人工的一致率」。

门禁化的做法：把 golden set 跑分接进 CI，任何对检索器 / prompt / 切分 / 模型的改动都触发评测，
**faithfulness 或 context recall 回退就当作失败的单元测试，阻断发布**。

### 3.7 效果数量级

- 朴素 RAG 在真实企业 query 上：**50–70%** 准确率。
- 高级 RAG（混合 + 重排 + 查询改写）：**80–90%**。
- 单加「混合检索 + 重排」这一段两步式：**提升 15–25 个百分点**（重排单步常被称为「所有优化里质量提升最大的一步」）。
- 代价：cross-encoder 重排增加 **150–500 ms** 延迟。
- 经验分布：BM25 权重在术语密集的企业知识库里通常占融合分的 **30–40%**；
  Dify 常规知识库问答 Top-3 召回率约 92%。

## 4. 分类法核实：四层记忆 / 四类检索

### 4.0 核实结论速览

| 判断 | 结论 |
|---|---|
| 四层记忆（会话/蒸馏/语义/程序） | **成立**，且与 AWS 官方分类（episodic / semantic / procedural + summary）互相印证 |
| 「三种检索形态」 | **标题写三种、正文列了四条**——编号笔误，四个形态本身都成立 |
| Mem0 的 graph layer | **本 pin（mem0 2.0.20, main）里没有实现**：`mem0/graphs/` 目录不存在，`graph_store` 只剩 `exceptions.py` 里 kuzu 的安装提示；但仓库自述 `AGENTS.md:54` 仍声称「Graph stores 4 providers」 |
| Bedrock「常组合知识图谱」 | **不准确**。AgentCore Memory 默认是「语义检索 + metadata 过滤 + namespace 隔离」，不是图；图要自己接 Neptune 等外部系统 |
| dsh「没有向量层」 | **成立**（全仓无 embedding / 向量库） |
| dsh「检索与模型看到同一份 foldSurface」 | **成立，且强于你的表述**——不是「尽量一致」，是**同一个纯函数** |
| dsh「无结构化代码检索」 | **不成立**（隐含推论）。仓库根有 `.codegraph/codegraph.db`，389 MB SQLite，外部 `codegraph` 工具提供 `node / callers / callees / impact` —— 它不在记忆层，但确实存在 |
| 分类法最大的口径问题 | 「**蒸馏层**」一个格子里混着三种语义完全不同的操作（改视图 / 改存储 / 派生新记录），工程含义差一个数量级 |

### 4.1 逐条核实：四层记忆

**（1）会话层（短期/工作记忆）✅ 成立。** 2026 年需要补两个细节：

- **会话层本身也开始 provider 化了。** OpenAI Agents SDK 把 `Session` 抽成接口
  （`get_items` / `add_items` / `pop_item` / `clear_session` 等五个异步方法），
  自带 `OpenAIConversationsSession`（接服务端 Conversations API）、`SQLiteSession`、
  `MemorySession`（进程内，开发用）。并且有互斥约束：**同一次 run 不能同时使用 `session`
  和 `conversation_id` / `previous_response_id`** —— 客户端管理历史和服务端管理历史是二选一。
- **`pop_item()` 这种「撤销最后一条」的能力被明确设计成用户纠错入口。**
  这对应 LangGraph 的 `update_state` / 时间旅行。

本项目：LangGraph checkpointer（`thread_id`）**已经是这一层的正确实现**，不需要改。

**（2）蒸馏层（情景记忆压缩）✅ 成立，但口径要拆。** 一个格子里实际上混着三种不同的操作：

| 实现 | 到底做了什么 | 谁受影响 |
|---|---|---|
| **dsh compaction** | 追加 `compaction/summary`（log-only）+ `compaction/prune`（log-only），真正的替换由紧随其后的 `user/message` 带 `surfaceOp replace` 完成，旧节点标 `shadowed` | **只改「模型视图」**。日志里全量保留，`shadowedSeqs` 可查 |
| **OpenAI `OpenAIResponsesCompactionSession`** | 一层 session 装饰器，超过阈值调 `responses.compact`，**清空并重写存储的历史** | **改存储**。SDK 会等 compaction 完成再结束这一轮；也可关掉自动、在阶段边界手动 `run_compaction({"force": True})` |
| **Bedrock AgentCore Summary 策略** | 把会话摘要**异步抽取成新的长期记忆记录**（`/summaries/{actorId}/{sessionId}`），原始 event 不动 | **派生新记录**。20–40 秒后才可见 |

dsh 是纯函数重放；OpenAI 是有损改写；Bedrock 是最终一致的异步派生。
写方案时不能说「我们做蒸馏」，必须写明是哪一种。

**本项目在蒸馏层是空的** —— 既没有摘要，也没有裁剪，长会话直接顶窗口。

### 4.2 逐条核实：四类检索

**（1）向量语义检索 ✅ 成立。** 补充：Cursor 的代码索引里，向量只是**两个索引之一** ——
另一个是 trigram/稀疏 n-gram 反向索引，专供正则与字面量搜索。它们不可互换
（向量答不了「找出所有 `db.execute` 传裸字符串的地方」，trigram 答不了「用户认证在哪」），
Cursor 的 harness 同时查两个，内部实测**语义搜索叠加在 grep 之上把 agent 准确率提升 12.5%**
（区间 6.5%–23.5%）。

**（2）混合检索 ✅ 成立，且是三家独立实现的共同点。**

- **Zep**：cosine + BM25 + BFS → 五种重排候选（RRF / MMR / mention 频次 / 图距离 / cross-encoder）
- **Mem0 2.0.20**：`(semantic + bm25 + entity_boost) / max_possible`，BM25 分数用 sigmoid
  归一化且参数随 query 词数自适应，**阈值先于融合**；`search()` 默认 `top_k=20`；
  还自带 5 个 reranker provider（Cohere / HuggingFace / LLM / Sentence-Transformer / Zero Entropy）
- **Azure Foundry**：官方措辞就是 hybrid search，`max_memories=5`
- **Bedrock**：`RetrievalConfig{top_k, relevance_score}` 按 namespace 分别配置

**这不是加分项，是入场券。**

**（3）结构化 / 图检索 ✅ 成立，但漏了第三条路。**
「知识图谱实体关联检索」成立。但 dsh 提供的是**另一个物种**：**可查询日志 + 血缘**。
`session-query` 给模型的五个操作：

| 操作 | 干什么 |
|---|---|
| `searchSessions` | 跨会话全文检索（FTS5，`unicode61`） |
| `searchEvents` | 会话内事件检索，可带 seq / time / type / **surface** 过滤 |
| `traceSession` | 血缘：祖先 + 后代（`parent_session` / `delegation_depth` / `seed_length`） |
| `traceEvent` | 单个事件的因果链 |
| `readEvent` | 按 seq 窗口读原文（`before` / `after`） |

索引建在**明确声明为可丢弃的派生库**上：`PRAGMA application_id` 防止误用别人的库、
schema 版本（当前 8）不符**就地重建**、`global_generation` 做增量对账、只读时只读 header。
这**不是「检索副本」，是同一份事实的另一种视图**。

**（4）代码感知检索 ✅ 成立，但要分清两条完全相反的路线。**

| 路线 | 代表 | 做法 |
|---|---|---|
| 建索引 | Cursor | tree-sitter AST 切块 → 向量入 Turbopuffer（数十亿向量、8000 万 namespace）+ trigram 反向索引；Merkle 树做增量；simhash 复用队友索引（中位仓库首查 7.87 s → 525 ms） |
| **不建索引** | Claude Code | 只给 Glob / Grep / Read，模型现场搜。2026-02 的 Amazon Science 论文测得：**关键词 agentic 检索可达 RAG 级性能的 90%+，且不需要向量库** |

**对本项目的意义很直接**：我们连「朴素的 metadata 保留 + 关键词检索」都还没做。
先补这两样的性价比，远高于直接上 pgvector。

### 5.1 dsh 六条差异化定位：逐条核实

1. **「没有向量层」** ✅ 成立。全仓 `grep -i embedding|vector store|pgvector`
   无任何记忆/检索相关的向量库；全文检索是 SQLite FTS5 `unicode61`。

2. **「检索与模型看到同一份 foldSurface」** ✅ **成立，而且比原表述更强**。落实到函数级：

   ```ts
   // packages/session-query/session-query/src/documents.ts
   import { foldSurface } from '@deepseek-ai/dsh-session'
   folded = foldSurface(events, currentSessionMessageProjections)   // 与派生模型历史同一个函数
   for (const seq of folded.nodes)        result.set(seq, 'current')
   for (const r of folded.replacements)
     for (const seq of r.shadowedSeqs)    result.set(seq, 'shadowed')   // 其余为 'log-only'
   ```

   每个 FTS 行都带 `surface` 列（`current` / `shadowed` / `log-only`），
   且 `surface` 是**可由工具过滤的 metadata**（`query.ts: buildEventWhere case 'surface'`）。
   所以更准确的表述是：**同一份 fold，全量可查，分层标记** ——
   不是「同源」，是「同一个纯函数 + 可过滤的可见性标记」。

3. **「确定性事件重放、可审计」** ✅ 成立。`extraction.ts: extractSessionEventText()`
   是纯 switch、无 LLM；`reasoning` 块**不产生任何可检索文本**；未知的声明合并事件
   **默认不可检索**，注释写得很硬：
   *「unknown blocks do not become searchable merely because their payload happens to contain strings」*。
   这是「显式优于隐式」的直接体现。

4. **「compaction = surfaceOp replace + shadowed 保留」** ✅ 成立。
   类型定义里 `compaction/start` / `summary` / `prune` / `end` 全部标注 `log-only, no surfaceOp`；
   真正的替换是紧随其后的 `user/message` 事件，且**相邻性是契约**
   （shadow price 协议：计量事件必须紧邻替换事件之前，消费者可以据此配对）。
   `shadowedSeqs` 是权威集合，`shadowedRange` 只是位置跨度（甚至可能 `start > end`）。

5. **「家谱/引用关系检索」** ✅ 成立。`persisted_sessions` 表存
   `parent_session` / `delegation_depth` / `seed_length` / `agent_preset`；
   工具 `traceSession` 返回祖先 + 后代，`traceEvent` 追单个事件。

6. **「与模型窗口同源」** ✅ 是第 2 条的推论，方向对。公平地补一句代价：
   **同源换来零漂移，代价是可检索范围被 surface 决定**。dsh 用「全量入索引 + `surface` 标记」
   把代价压到最小 —— 这恰恰是向量方案做不到的（向量库里没有「这条已被 shadow」的概念）。

**唯一需要修正的一条**：dsh 并非完全没有结构化代码检索，仓库根有
`.codegraph/codegraph.db`（389 MB）—— 只是 `codegraph` 是外挂工具，不在记忆层内。

#### 6.1.1 实测补充：不传 `index` 的真实行为（2026-09-18 补测）

原文写「`search(query=...)` 拿不到语义排序」，措辞偏温和。用 `DeterministicFakeEmbedding`
做过对照实验（`var/probe_store_index.py` / `probe_store_index2.py`，纯本地无网络）：

| 场景 | key 返回顺序 | score |
|---|---|---|
| **不传 `index`** | `r1, r2, r3, r4, r5` = **插入序**，两次运行完全一致 | **全部 `None`** |
| 传 `index` | `r3, r1, r4, r5, r2`（按相似度） | `0.134, 0.027, -0.017, ...` |
| 传 `index`，换不同 embedding | `r5, r3, r4, r1, r2`（排序随之改变） | 有值 |

三条判定：

1. **不传 `index` 时 `search(query=)` 不报错、也不降级为 `None`** —— 它返回结果，
   只是**按主键顺序**，且 `score` 恒为 `None`。**这是静默错误，不是功能缺失。**
   危害在于：调用方拿到的是「看起来正常的列表」，很容易误以为检索生效了。
2. **`put(index=[...])` 被静默忽略**（官方文档所述行为，已实测确认，不报错）。
3. **`score is None` 是唯一可靠的判据** —— 写读路径的防御性断言应断言它，
   而不是断言「结果非空」。

> 这正是 `docs/15` §3.4 引 Azure 那句「检索结果要能区分没找到和找到了」的本地实例：
> 当前形态连**「没检索」和「检索到」都区分不了**。

**表结构证据**：不传 `index` 时 SQLite 只有 `store` + `store_migrations` 两张表；
传了之后才多出 `store_vectors` + `vector_migrations`。也就是说**向量表根本没建**。

**store 里已有真实数据**（`var/memory_store.db`，8 行）：

```text
code-reviewer.<真实 user_uuid>  review-20260917  1892 字节   ← 真实审查结论，从未被读回
code-reviewer.<真实 user_uuid>  review-20260917    19 字节
code-reviewer.probe-*           review-2026*       21 字节   ← 探针残留
probe-interrupt-*               birthdate          35 字节
```

即：**记忆已经写进去了、而且写得对，但读路径一次都没执行过。**
这比「功能没做」更值得优先修 —— 数据已经在沉没。

| `var/chroma_db/` | **不存在** —— 向量库从未建成 |
| `data/` 语料 | 只有 1 个文件 `AcmeTech_Employee_Handbook.pdf`，4388 字节（8 KB） |

即：`scripts/create_chroma_db.py:31` 用的是 `os.environ["OPENAI_API_KEY"]`（会直接 KeyError），
`tools.py:89` 用的是 `OpenAIEmbeddings()` → 抛 `RuntimeError`。**两条路都堵着，建库和检索都跑不了。**

这条与 P0-5 直接相关，且提升它的优先级判断：P0-5（embedding 可配置 + 默认本地
`bge-small-zh`）**不是「优化项」，是「让入口 A 从不可用变为可用」的前提**。
在 P0-5 完成前，P0-3 / P0-4 / P0-6 全部无法验证 —— 没有语料能建库，就没有东西可测。

> 另一个被这个发现重新排序的点：语料只有 **8 KB**。在 8 KB 语料上谈
> 「混合检索」「cross-encoder 重排」是**没有意义的** —— 语料体量决定不了结论。
> P0-1/2（记忆层）的收益因此**高于**检索层改造：记忆层已有真实数据、且随使用自然增长，
> 检索层要先解决「有没有语料」这个前置问题。

**入口 B —— `src/agents/knowledge_base_agent.py`（AWS 固定管线式）**

图是写死的 `retrieve_documents → prepare_augmented_prompt → model → END`，
`numberOfResults=3`，需要 `AWS_KB_ID`。这是教科书级的 **Naive RAG**：
没有查询改写、没有重排、没有相关性判断、没有「证据不足就拒答」的分支——检索到什么就答什么。
但它有一个入口 A 没有的优点：**它保留并注入了 source / title / relevance_score**。

**结构性问题**：两个入口各自实现、互不复用，且 `tools.py` 里的 RAG 工具是放在
`agents` 层（与 agent 同层）而不是被 agent 消费的共享能力。

### 7.6 接口设计草案

```python
# src/rag/types.py
from pydantic import BaseModel


class Chunk(BaseModel):
    """检索结果的最小单元，携带可追溯来源。"""
    content: str
    parent_content: str | None = None   # 父子切片：交给模型的是父块
    source: str                          # 文件路径或文档 ID
    page: int | None = None
    score: float = 0.0
    score_details: dict[str, float] = {} # semantic / bm25 / rerank 各路分数


class RetrievalResult(BaseModel):
    """检索的统一返回：块 + 是否找到可信证据。"""
    chunks: list[Chunk]
    found: bool          # 显式区分"没找到"和"找到了"，不让调用方猜
    strategy: str        # 实际生效的策略，便于观测降级
```

```python
# src/rag/retriever.py
class RetrievePipeline:
    """查询改写 → 混合召回 → 融合 → 重排 → top-k。任一步失败都降级而非抛错。"""

    async def retrieve(self, query: str, *, top_k: int = 5) -> RetrievalResult: ...
```

降级链（保证永不因为检索挂掉而中断对话）：
`混合+重排` → `纯向量` → `空结果 + found=False`（由 agent 明确告知用户「资料里没有」，而不是编）。

## 8. 四条可移植结论

1. **照抄「事实层权威 + 检索层可丢弃」这个结构。** checkpointer 已经是追加式日志了
   （这一点和 dsh 同构），缺的是「派生索引」这个概念 —— 新增的检索层必须是
   **可重建的读模型**，不是第二个真相来源，并带 `revision` / `generation` 做增量对账。

2. **metadata 必须随索引走。** dsh 的 FTS 行带 `seq / type / time / surface`；
   我们的 `format_contexts` 把 `doc.metadata` 整个丢掉。
   补上之后回答里才能出现 `[来源: xxx | 片段: n]`。

3. **优先级排序：蒸馏层 > 混合检索 > pgvector。** 蒸馏层当时是空的，
   而长会话顶窗口是**必然会发生**的事故；三家企业都做了，OpenAI 的版本甚至只是一层
   session 装饰器（wrap + 阈值 + 手动 force）。它的实现成本远低于上 pgvector。
   反过来 pgvector 能力上限最高但眼下最不急。

   **2026-09-18 实测后的补充排序**：在 P0 内部，**记忆层（P0-1/P0-2）优先于检索层改造**。
   依据是语料体量 —— `data/` 只有 **1 个 4388 字节的 PDF**（8 KB），
   在这个体量上谈混合检索与 cross-encoder 重排没有意义，结论无法由数据支撑；
   而记忆层已有真实数据（`var/memory_store.db` 里 8 行、含一条 1892 字节的真实审查结论）
   且随使用自然增长。**P0-5 则是检索侧的前置条件**：embedding 不可配置时，
   P0-3/P0-4/P0-6 全部无法验证。三项均已于 2026-09-18 落地（§7.2.1）。

   **2026-09-18 晚的补充**：蒸馏层（P0-7）已实现，但**在两条生产路径上都没生效**
   （§7.2.3）—— 「蒸馏层不再是空的」目前只对**写入**成立，对**读取**仍不成立。
   排序不变，但 P0-7 的收尾（把折叠收敛到唯一的读取点）应排在 P0-8 / P0-9 之前：
   它是已实现待接线，成本低于从零起的两项。

4. **混合检索可以先用 SQLite FTS5 起步。** dsh 用单表 FTS5 就撑起跨会话检索，
   零新服务、零 Docker，和本项目「clone 下来就能跑」的约束一致。
   中文注意：`unicode61` 对中文按字切，可用但召回一般，需要换 tokenizer（trigram 或接 jieba）。
