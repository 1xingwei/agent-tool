# 注释中文化与译文审校

> 本文合并自同一条工作流的前后两段：**中文化**（把全仓英文注释与文档字符串改成中文）
> 与**审校**（核查译文本身对不对）。前者保证「代码本体零改动」，
> 那只能证明没改坏代码，不能证明译文正确 —— 后者补上那一环。
>
> 时间：2026-09-17。涉及 `src/`、`tests/`、`scripts/`、`docker/`、`docs/` 与根目录配置。

| 阶段 | 范围 | 产出 |
|---|---|---|
| 中文化 | 89 个文件、1037 个翻译单元、2287 行原文 | 代码注释与文档字符串全部中文 |
| 审校 | 1037 个单元（含中文的 1013 个）+ 9 篇英文文档、82 节、963 行 | 查出 **14 处真缺陷**，全部修好 |

## 一、做法

不能靠「全文重写」—— 那样代码本体也会被顺手改掉。流程改成三步：

1. **抽取**（`var/build_units.py`）：用 `tokenize` 拿到每个注释与文档字符串的
   精确字符区间，按「连续同缩进的注释行合并成一段」切出翻译单元。合并是必要的：
   英文原文常把一个段落折成 4–5 个 `#` 行，逐行翻译会把句子翻散。
2. **翻译 + 校验**（`var/translate_units.py`、`var/recheck.py`）：按 token 预算分批
   送模型，译文以单元 id 回填；随后做块级复检 —— 原文里的反引号内容、
   snake_case 标识符、文件名、路由、函数调用必须全部出现在译文里。
3. **回写**（`var/apply_translations.py`）：只替换 token 区间，同一文件内自底向上
   替换避免行号漂移，行尾（CRLF/LF）与文件末尾换行按原样保留。
   注释只换注释文本，前面的缩进或行内代码原样拼回。

## 二、保证：代码本体零改动

回写后用 `var/verify_apply.py` 做了一次强校验：把改前快照与改后文件都过一遍
`tokenize`，剔除注释与文档字符串后比对记号序列——**89 个文件的代码本体逐 token
完全一致**，非 Python 文件剥掉注释后逐行相同。这轮改动不可能改变运行时行为。

顺带确认：`.env`、`.env.example`、`compose.yaml` 等配置文件的非注释内容一行未动。

> **后续的一处说明性改动**：文档目录后来做过两次收敛重命名（扁平化、以及
> 「审核 + 接口检查 + 修复记录」三篇合并等），源码注释里引用的文档路径随之同步。
> 这类改动只动注释文本，仍不影响「代码本体逐 token 一致」这一结论的适用范围 ——
> 上面那句是对**中文化那一轮**快照的比较，不是对仓库当前状态的持续断言。

## 四、审校：方法与范围

三层校验，外加一步校准。

| 层 | 做什么 | 工具 |
|---|---|---|
| 结构层 | 把仓库当前文件重新按同一套 `tokenize` 规则抽一遍，与译文台账逐块比对，确认「文件里的中文」就是台账里的中文 | `var/verify_pairs.py`、`var/verify_applied_text.py` |
| 机械层 | 数字、URL、反引号内容、代码标识符、表格行数、代码围栏数、列表项数是否与原文一一对应 | `var/audit_translations.py`、`var/audit_docs.py` |
| 语义层 | 把「英文原文 ↔ 中文译文」成对交给模型逐条审校，只报问题 | 同上（`--zh-file`） |
| 完整性 | 扫出所有**仍是英文散文**的注释行、以及**没被任何翻译单元覆盖**的行 | `var/scan_english_prose.py`、`var/find_uncovered.py` |

**先校准再用模型。** 直接问模型「这段翻译对不对」，它多半会盖章通过。
所以先用 10 条人工构造的样本试它：6 条含真实缺陷（否定词译反、因果颠倒、
整句漏译、术语错译、区块标记被译掉、数值改错）+ 4 条正常译文（含「术语保留英文」
「中文比英文短」这类容易误报的情形）。结果 **6/6 全抓到、1 条风格性误报**，
说明它能用，才拿它跑全量 1037 个单元 + 82 个文档章节。

| 审校对象 | 规模 |
|---|---|
| 代码注释 / 文档字符串 | 1037 个单元（其中含中文的 1013 个） |
| 从英文翻译的文档 | 9 篇、82 节、963 行英文 |
| 中文原生文档（不涉及翻译） | 8 篇 |

9 篇英文文档原文件名分别是 `AGUI.md`、`RAG_Assistant.md`、`GitHub_MCP_Agent.md`、
`File_Based_Credentials.md`、`VertexAI.md`、`Ollama.md`，以及
`superpowers/specs/` 与 `notes/` 下的三篇（审查、能力方案、简历对齐）。
两边标题数完全一致，因此按章节序号一一配对。

## 六、4 处整块漏译的根因

抽取判据是「**含英文且不含中文** → 需要翻译」。它有两处盲区：

1. **块里混进了中文 → 整块被判为「已翻译」。** 文档改名后，引用路径变成
   `docs/02-AG-UI协议支持.md`、`docs/11-Agent能力完善方案.md`，路径里的中文
   把 `agui.py` 的模块文档字符串和 `llm.py` 的函数文档字符串整块救了出去，
   于是从没进过翻译清单（#10、#11）。
2. **合并会被打断，掉队的行没人管。** 一个注释块要求「连续且前缀相同」才能合并成单元；
   中间有一行被判据排除，块就断在那里，而那一行**既不在前块也不在后块**
   （#9、#12 都是这种）。

处置：不再依赖块级语言判断，改成**逐行**扫描英文散文（`var/scan_english_prose.py`），
并补了一条「中英混排行」判据——`# .strip() into an AttributeError (see docs/10-审核与修复总账.md).`
这种「中文藏在路径里、英文才是正文」的行，正是前一个判据的盲区。

## 七、审校工具自己踩的坑（方法学，值得复用）

1. **RST 双反引号 vs Markdown 代码围栏。** 文档里的 ` ``` ` 会被成对的双反引号
   匹配吞掉，产出 30 多条「反引号内容丢失」的假报。比对前必须先剥掉围栏代码块。
2. **URL 后面紧跟行文标点。** `(https://console.cloud.google.com/billing).` 直接比对
   必然判定「URL 被改写」，要先剥掉尾随的 `).`。
3. **别把「原注释自己写错的词」当代码引用。** `Application_name` 是原注释的笔误
   （代码里是 `application_name`），要求译文保留它是错的。标识符校验要先用
   「仓库代码里真实出现过的名字」过滤一遍。
4. **「整行含中文就跳过」会藏住中英混排残留。** 见 §六，这条判据正是漏译的成因。
5. **同一文件不要在同一批次里发两个编辑。** 并发读改写会互相覆盖——实测有一处
   编辑被静默吞掉（后来复查文件时才发现）。改完必须 grep 确认落盘。
6. **`ruff format` 会 dedent 文档字符串正文的缩进，也会改变代码折行。**
   中文比英文紧凑，原本因为行太长而折成三行的调用链，注释一变短就够放在一行了。
   CI 里有 `ruff format --check`，所以回写后必须补跑一次 `ruff format`（本次命中 3 个文件）。
   这次格式化只移动空白、不动记号序列，不影响 §二 的逐 token 校验结论。
7. **文档字符串末尾的占位空行会被模型吞掉。** 回写逻辑直接取最后一行当正文时，
   正文末行会被误当成占位行丢弃。做法是先归一化：末行为空则先剥掉，
   再据「结尾引号是否独占一行」重建。
8. **校准不能省。** 不先用已知缺陷样本试过审校模型，就无法判断它「0 问题」是真干净
   还是根本没在查。
