# 架构说明

这份文档讲的是「骨架」，不是「某个 agent 有多聪明」。本项目的定位是一套
**骨架固定、能力可插**的 Agent 服务模板：契约、鉴权、记忆、流式、可观测性
这些不该重复实现的部分被压缩到 `src/service` 与 `src/core` 里只做一次，
业务复杂度全部收在 `src/agents` 目录内。新增一个 agent 只需要写一个图
加注册表里一行，服务层不用改。

与本文互补的材料：

- 上游 README 的 `Architecture Diagram` 与 `Key Features`（概览层）
- `docs/10-审核与修复总账.md`：13 条路由的鉴权与状态实测矩阵、全项目审核结论、
  逐项缺陷的根因与修法、落地与验证矩阵（同一份记录，已合并去重）

## 一、五层骨架

```text
前端与调用方    Streamlit UI :8501 · AgentClient SDK · run_client 示例
      ↓
HTTP 协议层     Bearer 鉴权（verify_bearer）· 13 条路由 · AG-UI 独立协议路由
      ↓
服务编排        _handle_input（中断检测）· message_generator（SSE 合成）· threads 枚举
      ↓
图运行时        agents 注册表 → get_agent → LangGraph 图（StateGraph / @entrypoint）
      ↓
基础设施        checkpointer 四后端 · store 长期记忆 · LLM 工厂 · LangSmith / LangFuse
```

各层的职责边界与它**不**知道的事情：

| 层 | 目录 | 它知道什么 | 它不知道什么 |
|---|---|---|---|
| 契约层 | `src/schema/` | 全部 Pydantic 模型、12 家模型厂商的枚举 | 任何业务逻辑 |
| 配置与工厂 | `src/core/` | `settings` 单例、`get_model()` 按厂商分发模型 | 具体 agent 的存在 |
| 存储适配 | `src/memory/` | 四后端的 `initialize_database` / `initialize_store` | 会话内容 |
| 业务图 | `src/agents/` | 12 个图各自的节点与工具 | HTTP、鉴权、SSE |
| 服务编排 | `src/service/` | 路由、鉴权、输入解析、SSE 合成 | **任何一个具体 agent** |
| 客户端 | `src/client/` | HTTP 调用与 SSE 解析、`AgentClient` | 服务端实现细节 |
| 语音 | `src/voice/` | STT / TTS provider 抽象（默认关闭） | agent |

### 依赖方向的铁律

**服务层不认识任何具体 agent。** 这一点可以直接验证：`src/service/service.py`
的全部 import 中，来自 `agents` 包的只有
`DEFAULT_AGENT / AgentGraph / get_agent / get_all_agent_info / load_agent`
五个符号，没有任何一行 import 具体的 agent 模块。服务层只认注册表这个字典。

**`agents` 层不反向依赖 `service`。** 全量 grep 确认 `src/agents/` 对 `service`
零引用。这条约束的意义在于：跨模块共享的领域工具函数可以放在 `service/utils.py`
而不会成环——但「不成环」不等于「可以随便放」。把未知 agent_id 映射为 404 的
`_resolve_agent` 最终落在 `service/service.py`：因为整个 service 层测试的 patch 缝
都打在 `service.service.get_agent` 上（113 处引用 / 12 个 patch 目标），
移到 `utils.py` 会让这些 patch 静默失效。取舍记录见
`docs/10-审核与修复总账.md` §7.2。

反过来，`service.agui` **绝不能** import `service.service`——`service.py` 在模块
顶部 import 了它，反向依赖会在模块只执行到一半时抛 `ImportError`。这一点有
三例对照的实测记录，见 `docs/10-审核与修复总账.md` §7.2。

**契约集中在 `src/schema/`。** 跨层通信只用 Pydantic 模型，没有裸 dict
在层间流动。这是这套骨架能被复用的前提：换前端时，只需要新的前端能解析
同一套 `ChatMessage`。

## 二、路由清单

| 路由 | 方法 | 鉴权 | 说明 |
|---|---|---|---|
| `/health` | GET | 豁免 | 唯一挂在 `app` 而非 `router` 上的路由 |
| `/info` | GET | 需要 | 返回 12 个 agent、可用模型、默认 agent 与默认模型 |
| `/invoke` | POST | 需要 | 非流式，返回最后一条消息或中断值 |
| `/{agent_id}/invoke` | POST | 需要 | 同上，指定 agent |
| `/stream` | POST | 需要 | SSE 流式 |
| `/{agent_id}/stream` | POST | 需要 | 同上，指定 agent |
| `/history` | POST | 需要 | 按 `thread_id` 读回消息历史 |
| `/{agent_id}/history` | POST | 需要 | 同上，指定 agent |
| `/threads` | GET | 需要 | 按 `user_id` 列出 thread 列表 |
| `/{agent_id}/threads` | GET | 需要 | 同上，指定 agent |
| `/feedback` | POST | 需要 | 打分写回 LangSmith；未配 key 时按设计 no-op |
| `/agui/run` | POST | 需要 | AG-UI 协议事件流 |
| `/agui/{agent_id}/run` | POST | 需要 | 同上，指定 agent |

鉴权是统一的：`router = APIRouter(dependencies=[Depends(verify_bearer)])`，
AG-UI 路由通过 `router.include_router(agui_router)` 继承同一份依赖，因此
两条协议出口的鉴权行为一致。`DEFAULT_AGENT` 为 `research-assistant`。

## 三、一次请求的完整链路

以 `POST /stream` 为例，自上而下穿透五层：

```text
步骤  所在层          做什么
----  --------------  ------------------------------------------------------------
 1    前端            用户输入
 2    客户端          POST /stream，带 Bearer token
 3    服务路由        鉴权 → agent 预检（未知 agent_id 在此提前返回 404）
 4    服务编排        _handle_input：aget_state 查中断 → Command(resume=…) 或新消息 → 读取侧折叠（可选）
 5    服务编排        astream(updates, messages, custom, subgraphs=True)
 6    LangGraph 图    逐节点执行，每个节点后由 checkpointer 落盘
 7    服务路由        SSE 下发：token 增量与 message 中间步骤，末尾 [DONE]
 8    客户端          解析为 ChatMessage 对象
 9    前端            逐字渲染
```

第 3 步的预检是必需的，而不是冗余：`message_generator` 是异步生成器，函数体
直到首次迭代才执行，若把校验留在里面，异常发生时 `StreamingResponse` 早已
提交 200，状态码无从改判——表现为「200 加空响应体」，客户端认为成功却一直
等不到内容。

### `_handle_input` 承担的四件事

这个函数是服务层的核心，它在调用图之前完成四件工作：

1. **生成或复用标识**：`run_id`（新生成，用于反馈关联）、`thread_id`、
   `user_id`（缺失时各自新建 UUID）。三者都进 `RunnableConfig.configurable`。
2. **中断恢复判定**：先 `agent.aget_state(config)`，从 `state.tasks` 里筛出
   带 `interrupts` 的任务。有中断则把用户输入包装成 `Command(resume=...)`，
   否则包装成 `{"messages": [HumanMessage(...)]}`。这就是 human-in-the-loop
   不需要服务层写任何分支逻辑的原因——判断依据是图的状态，不是 agent 名字。
3. **配置组装与保护**：`agent_config` 会并入 `configurable`，但 `thread_id`、
   `user_id`、`model` 是保留键，命中即 422。LangFuse 的 CallbackHandler 也在
   这里按开关挂上。
4. **会话蒸馏的读取侧折叠**：折叠发生在**模型视图构造点**（`graph_factory._wrap_model`
   的 `build_messages`，各 agent 的 `wrap_model` 都是它的薄转发），`apply_distillation`
   把历史折叠成 `[摘要, ...最近若干条]` 后交给模型。**只改写送给模型的这一份**，
   checkpoint 原文一条不动，所以 `/history` 仍是全量。恢复 interrupt 时输入是
   `Command` 控制指令，不进模型视图。

值得单独提一句的是 `/invoke` 的返回策略：它取 `stream_mode=["updates", "values"]`
的**最后一个事件**，并优先检查 `__interrupt__`。这意味着当一个 agent 产出多条
`AIMessage`（例如 `bg-task-agent` 的后台步骤、`research-assistant` 的工具步骤）时，
中间消息会被丢弃，只返回最终答复。这是有意为之的简化，代码注释里写明了。

## 四、记忆子系统

LangGraph 把记忆拆成两个独立组件，本项目把两者的后端都可配置化：

| | checkpointer | store |
|---|---|---|
| 作用域 | thread 级（随会话走） | 跨会话（按 namespace 隔离） |
| 典型内容 | 消息历史、图状态、中断点 | 长期事实、用户偏好（如 `interrupt-agent` 记住的生日） |
| 落盘时机 | 每个节点执行后 | 节点内显式读写 |
| 谁在用 | 全部 agent（图状态自动写入） | 全部图都被挂上，实际读写的是 `interrupt-agent` |
| 初始化 | `initialize_database()` | `initialize_store()` |

后端选择的优先级在 `src/memory/__init__.py` 里，顺序即优先级：

1. `REDIS_URL` 一旦设置，**同时接管** checkpointer 与 store，优先级最高
2. 否则按 `DATABASE_TYPE` 选 Postgres / MongoDB
3. 都没有则回落到 SQLite（本机默认，落在 `var/`）

MongoDB 目前只有 checkpointer 实现，store 会回落到 SQLite。

### thread 列表是从 checkpointer 反推的

`/threads` **没有自己的表**。`src/service/threads.py` 直接读 checkpointer 的
checkpoint 元数据来枚举会话列表。这是个明确的取舍：

- 收益：少一张表、少一处写入点，不存在「表与 checkpointer 不同步」的问题
- 代价：必须复刻 LangGraph 的 checkpoint 写入约定。该文件顶部那三个常量就是
  在给这个耦合兜底——`THREAD_HEAD_STEP = -1`（每 thread 的首个检查点在 step -1，
  单轮会话永远到不了 step 1）、`MAX_THREAD_HEADS = 200`、`MAX_HEAD_ROWS = 1000`
  （带子图的 agent 会写多份继承父级 metadata 的 head 行，需要分页去重）

排序也是近似的：先按 thread 创建顺序取 head，再按 tip 的 checkpoint ID 重排，
以逼近「最近更新」。「updated_at」取的是 tip 的 `ts`，`title` 取首条人类消息
前 60 字符。

跨用户隔离在读取时就地校验：如果 checkpointer 返回的行其 `metadata.user_id`
与请求不符，会打 warning 并跳过该行，宁可少列也不越权。

### 会话蒸馏：折叠的是「视图」，不是存储

checkpointer 里存的是**事实**，送给模型的是**视图**，`src/core/distill.py` 只改写后者：

- `plan_distillation()` 判定是否触发（条数阈值 + 最少新增条数 + 保留窗口），
  `apply_distillation()` 产出 `[摘要, ...尾部]` 这份模型视图。
- **原文一条不删**：`/history` 与 checkpoint 永远是全量，摘要只活在模型视图里。
  口径属 dsh 那一支（`surfaceOp replace` + 原文可查），辨析见
  `docs/15-记忆与检索层-对标核实与行动清单.md` §4.1。
- `DISTILL_ENABLED` 默认 **False**，不配置即零行为变化。
- 读取侧已接通：`graph_factory._wrap_model` 的 `build_messages` 构造模型视图时调用
  `apply_distillation`（service 侧 `_distill_input` 已删除——它造出的折叠 input 会被
  `add_messages` 合并回全量，等于没折，见 `docs/15` §7.2.3）。

## 五、图装配机制

12 个 agent 挂在 `src/agents/agents.py` 的注册表里。它们的构造方式其实有**四种**：

| 构造方式 | 返回类型 | 数量 | 使用者 |
|---|---|---|---|
| `build_tool_agent_graph(...)` 工厂 | `CompiledStateGraph` | 3 | `code-reviewer`（挂记忆/蒸馏/审批节点）、`research-assistant`、`rag-assistant`（`src/agents/graph_factory.py`） |
| `StateGraph(...).compile()` 手写 | `CompiledStateGraph` | 5 | `loop-agent`、`command-agent`、`bg-task-agent`、`interrupt-agent`、`knowledge-base-agent` |
| `create_supervisor(...).compile()` | `CompiledStateGraph` | 2 | 两个 supervisor（委托给 `langgraph_supervisor` 库建图） |
| `@entrypoint()` | `Pregel` | 1 | `chatbot` |
| 继承 `LazyLoadingAgent` | 异步 `load()` 后才产出图 | 1 | `github-mcp-agent` |

前三种在模块导入时就绪，第四种不行——MCP 客户端要在事件循环里建连接，
而模块导入是同步的。`LazyLoadingAgent` 就是为这一处异步初始化需求引入的抽象，
它把「建图」推迟到服务启动。

为了统一这四种形态，`get_agent()` 把返回值收敛成一个类型别名
`AgentGraph = CompiledStateGraph | Pregel`，调用方不需要知道自己拿到的是哪种。

### lifespan 装配

服务启动时 `lifespan` 执行一次装配，把记忆交给每个图：

```text
agents 注册表（12 项）
   ├── 已编译的图（11 个）────┐
   └── LazyLoadingAgent（1 个）─┤（先 await load()）
                               ↓
                    lifespan 装配（启动时执行一次）
                    对每个图：调 setup()，写入 checkpointer 与 store
                               ↓
                    请求期：get_agent(agent_id) 直接取用
```

一个图加载失败不会阻断启动——循环里捕获异常后打日志继续，只跳过那一个 agent。

**这里有个不优雅但必要的妥协**：记忆是通过直接改属性注入的
（`agent.checkpointer = saver`），而不是构造时传参。原因是四种构造方式无法
统一传参，而下游 LangGraph 恰好读取这两个属性名。代价是这层注入绕过了类型
系统，类型检查器看不到。

## 六、流式与双协议出口

```text
updates（节点级状态变更）──┐
messages（token 级增量）───┼→ message_generator 归一化 → ├→ SSE 自定义协议 /stream
custom（业务自定义推送）───┘   （抽帧 · 去重 ·              └→ AG-UI 标准协议 /agui/run
                                统一为 ChatMessage）
```

`message_generator` 同时订阅三种 stream mode，把异构事件归一化成
`ChatMessage` 后再下发。归一化过程中有两处值得注意的处理：

- **上游回显去重**：LangGraph 会把输入消息回传一次，代码按「type 为 human 且
  内容等于本次输入」丢弃，否则前端会看到自己刚发的话重复出现。
- **supervisor 特例**：`langgraph-supervisor` 库的节点会产出大量转交工具消息，
  代码按节点名（含 `supervisor` / `sub-agent`）裁剪，只保留有信息量的那几条。

SSE 帧格式是自定义的 JSON：

```text
data: {"type": "message", "content": {...ChatMessage...}}
data: {"type": "token", "content": "逐字"}
data: [DONE]
```

`stream_tokens=false` 时只发 `message` 帧、抑制 `token` 帧，用于只需要中间步骤
不需要逐字的场景。另外带 `skip_stream` tag 的节点（如 `interrupt-agent` 内部的
结构化输出提取）不会泄漏到 token 流里。

**AG-UI 是同一张图的第二条出口。** `src/service/agui.py` 用 `LangGraphAgent`
把图包装成标准 AG-UI 事件流，使非 Streamlit 的前端（如 CopilotKit）也能接入。
代价是双份维护——`agui.py` 与 `service.py` 各写了一套逻辑，已有的缺陷 B
（未知 agent_id 的处理）就是这种重复出问题的实例。

## 七、agent 层

12 个 agent 覆盖了 LangGraph 的主要范式：

| 范式 | agent | 演示内容 |
|---|---|---|
| 最简 functional API | `chatbot` | `@entrypoint`，23 行 |
| 工具调用循环 | `research-assistant`、`loop-agent`、`code-reviewer` | ReAct 的三种写法：内置循环 / 手写循环 / 领域工具 |
| 多 agent 调度 | `langgraph-supervisor-agent`、`langgraph-supervisor-hierarchy-agent` | 单层与嵌套两层转交 |
| 显式流程控制 | `command-agent` | `Command` 手动跳转 |
| 异步任务 | `bg-task-agent` | `custom` 流模式推中间进度 |
| 人机协同 | `interrupt-agent` | 中断 → 等待 → `Command(resume=...)` |
| 检索增强 | `rag-assistant`、`knowledge-base-agent` | 自建向量库 vs 托管知识库 |
| 外部协议 | `github-mcp-agent` | 真实 MCP 客户端 |

本机可用性分两类：9 个可直接演示；`rag-assistant`、`knowledge-base-agent`、
`github-mcp-agent` 代码与接线就位但缺外部凭证（后两者的降级是静默的，
接口仍返回 200）。逐项的凭证依赖与失败方式见 `docs/13-面试材料与岗位对照.md`。

## 八、扩展一个新 agent

完整成本是两步：

1. 在 `src/agents/` 新建模块，导出编译好的图
   （`StateGraph(...).compile()`、`@entrypoint()` 或继承 `LazyLoadingAgent`）
2. 在 `src/agents/agents.py` 的 `agents` 字典里加一行，附一句 description

服务层不用改任何代码，以下能力自动获得：

- `/{agent_id}/invoke`、`/{agent_id}/stream`、`/{agent_id}/history`、
  `/{agent_id}/threads` 四条路由
- `POST /agui/{agent_id}/run` 的 AG-UI 事件流
- Bearer 鉴权
- 启动时自动装配 checkpointer 与 store（thread 持久化、中断恢复因此可用）
- `/info` 里的能力清单（Streamlit 的 agent 下拉框从中读取）
- 反馈、追踪、SSE 两路流式

也就是说，新增 agent 的风险面仅限「图本身写得对不对」，与平台无关。

## 九、设计取舍与已知边界

这些是本架构里刻意选择的权衡，不是遗漏。

**记忆注入走属性赋值而非构造参数。** 四种异构构造方式换来的必然妥协，
见第五章。收益是加 agent 不动服务层。

**`/threads` 反推 checkpoint 而非独立建表。** 省一张表，代价是耦合
LangGraph 的内部写入约定，且「最近更新」是近似值，见第四章。

**鉴权是全站开关式的。** `AUTH_SECRET` 未配置时，服务只在启动日志里打一条
warning，然后**所有接口敞开**。作为内网演示项目是合理取舍；若要对外部署，
这是第一个必须改的地方。

**双协议出口意味着双份维护。** 见第六章。

**默认单进程。** 本机用 SQLite 局部文件，图实例与 checkpointer 一一对应。
横向扩容需要换成 Postgres 或 Redis 后端，`var/checkpoints.db` 这类本地文件
无法跨实例共享。

**三类能力在本机不生效**，因为缺外部凭证而非代码缺陷：safeguard 内容过滤
（缺 Groq key，恒返回 SAFE）、语音输入输出（按设计留空即关闭）、天气工具
（缺 OpenWeatherMap key 时不注册）。这类能力的正确口径是「代码已实现并接入，
本机未配置对应凭证，因此未做端到端验证」。

**两处测试仍偏弱**：`tests/agents/test_loop_agent.py` 与
`tests/agents/test_supervisor_smoke.py` 早期版本只断言「图能编译」。
编译通过不等于调用不炸，这类断言是历史缺陷的漏检来源；现已补入驱动真实
调用链路的用例，但同类弱断言仍是后续审查的重点。
