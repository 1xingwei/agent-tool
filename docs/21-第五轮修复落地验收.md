## 五、本轮新发现

### V1（P2 · 测试隔离）两条 F5 新用例把「真实 lifespan」引进测试套件，会创建生产 `var/` 下的库

`tests/service/test_agui.py:165` 与 `tests/service/test_service.py:287` 用的是
`with TestClient(app, ...) as client:` —— **上下文管理器形式会真的跑 lifespan**，
于是 `initialize_database()` / `initialize_store()` 会去开 `settings.SQLITE_DB_PATH`
（`var/checkpoints.db`）与 `settings.SQLITE_STORE_PATH`（`var/memory_store.db`）。

两个决定性实验（移走 → 跑用例 → 看是否被重建 → 还原并校验 sha256）：

```text
移走 var/memory_store.db   → 跑两条 F5 用例      → 文件被重建（36864 B，mtime 09-19 16:09）
移走 var/checkpoints.db    → 跑 test_unloaded_agent_returns_500 → 文件被重建（20480 B，mtime 09-19 16:31）
两次实验后均已还原，sha256 与实验前一致（aaddad784742e44e / 92e8bda78f277c41）
```

**必须说清的边界**：今天它们**只建不写** —— `setup()` 是 `CREATE TABLE IF NOT EXISTS`，
所以跑完全套测试后三个库的 sha256 未变（§3.1）。问题不在「已经毁数据」，而在三件事：

1. **fresh clone 上跑一次测试，会凭空生成「生产」库**。这与 R1 的形态完全一致：
   测试代码把生产路径当成自己的临时目录。
2. 触发点从 **1 个增加到 3 个**。既有触发点是 `tests/service/conftest.py:74` 的
   `mock_httpx` fixture（`with TestClient(app)`），被 `tests/service/test_service_e2e.py:91` 使用；
   本轮新增的两条用例复制了这个模式。**W1 的假设恰恰是 `var/` 下 SQLite 的跨进程竞争**
   （`docs/20` §2.2），多两个打开者就是多两个争用面。
3. R1 的修法（`tests/conftest.py` 的 autouse fixture）**只隔离了 `CHROMA_FTS_DB`**，
   没有覆盖 `SQLITE_DB_PATH` / `SQLITE_STORE_PATH` —— 同一个洞的**第二扇门**。

这正好把 `docs/19` §9.5 的教训复制了一遍：**枚举污染点必须全量 `grep`，不能按文件下判断。**
当时的结论是「堵点修 + conftest 兜底」，本轮只做了「点」，兜底没跟着扩。

**建议修法**（与 R1 完全同型，一处改动覆盖全部触发点）：

```python
# tests/conftest.py，紧挨现成的 _isolate_fts_sidecar
@pytest.fixture(autouse=True)
def _isolate_runtime_dbs(tmp_path, monkeypatch):
    monkeypatch.setattr(settings, "SQLITE_DB_PATH", str(tmp_path / "checkpoints.db"))
    monkeypatch.setattr(settings, "SQLITE_STORE_PATH", str(tmp_path / "memory_store.db"))
```

**验收判据**：移走 `var/memory_store.db` 与 `var/checkpoints.db`，跑全套测试，
两个文件**都不应**被创建（修复前必然被创建，已实测）。

### V2（P3 · F3 残留）denylist 是「精确名单」，漏掉 `.env.*` 家族与 `.db`

`code/tools.py:10-18` 的 `_SENSITIVE_PARTS` 用**精确相等**匹配 path 的每一段，
后缀表只有 `.pem / .key / .sqlite`。实测（`var/audit6/probe_G_residuals.py`，在 tmp 仓库里造文件，不碰真 `.env`）：

```text
.env                   拦        .env.local           **放行**
.env.example           拦        .env.production      **放行**
privatecredentials/**  拦        config/.env.staging  **放行**
certs/server.pem       拦        certs/id_rsa         **放行**
var/chroma_fts.sqlite  拦        var/checkpoints.db   **放行**
                                  service-account.json **放行**

端到端（tmp 仓库里放 .env.local / .env.production / app.db）：
  read_file('.env.local')       → ❌ 读到了明文
  read_file('.env.production')  → ❌ 读到了明文
  read_file('app.db')           → ❌ 读到了明文
  file_search(content_pattern='AUTH_SECRET') → 三个文件全部命中
```

也就是说：**本轮修掉的是「这个仓库恰好用的那几个名字」**，而不是「密钥类文件」。
`.env.local` / `.env.production` 是最常见的写法之一；`.db` 更是本仓自己的运行时库后缀
（清单里有 `.sqlite` 却没有 `.db`，属同类漏项）。

**修法**：把「精确段名」换成「模式」——`name == ".env" or name.startswith(".env.")`、
后缀表补 `.db`、可选加 `id_rsa*` 与 `service-account*.json`。
**验收判据**：新增用例断言 `read_file(".env.local")` 被拒（现在的三条用例都只覆盖精确名，注入反例不会变红）。

### V5（P4 · 测试质量）一处恒真断言

`tests/agents/test_code_reviewer.py:145`：

```python
assert all("^env.md" not in line or True for line in hits.splitlines())
```

`or True` 让这个断言恒为真 —— 正是本仓反复强调的「判据要能真的失败」的反面。

## 十、方法论备忘（本轮我自己的两次踩坑）

### 10.1 注入探针被沙箱的「累积删除计数器」截断两次

v1：每例在 `src/` 里建一个 `<源文件>.aicbak`、跑完删掉 —— 累计到第 50 次删除时撞上
`SAFE_DELETE_BULK_CONFIRM_REQUIRED`（`scope: "turn"`，阈值 50），脚本被拦腰截断并**留下了一个未恢复的注入**。

v2：改成把备份放 `var/audit6/bak/`，但**所有用例共用一个 `--basetemp`** ——
pytest 每次启动都会先清空该目录，删除量再次累积到阈值，
表现是**后 9 个用例全部 `rc=1` 但输出里既没有 `1 failed` 也没有 `1 passed`**（子进程被拦）。

v3：备份移出 `src/`、**每例一个全新的 `--basetemp`**（不存在就无需清空，删除了 0 次）、
哨兵用**内容**（`STATE=running` → `STATE=done`）代替「存在与否」（沙箱拦删除，不拦改写）。
v3 一次跑通 12 例。

**顺带暴露的一件事**：v1 中断后留下的 `.aicbak` 与注入都要靠**自愈**才被发现。
两次都验证了 `docs/19` §9.1 的规范是对的 —— 注入式探针必须有启动自愈，`finally` 挡不住沙箱拦截。

### 10.2 我的状态校验脚本第一版误报 4 处「状态不对」

`var/audit6/verify_state.py` 原本对每个注入点断言「新代码出现 1 次 **且** 旧代码出现 0 次」，
结果 4 处报错，全是**判据本身写错**：

- `F1-async` / `F1-sync` / `F7`：旧代码（裸的 `await self.model.ainvoke(...)`）本身就是
  新代码（`try:` 包住它）的**子串** → 天然出现 1 次，不是残留。
- `F3-read_file`：注入动作是「整段删除」，旧代码是**空串** → `"".count` 恒等于 len+1 = 5061。

修法：**先把新代码整段抹掉，再看剩余文本里有没有旧行为**；空串直接跳过。
两次踩坑都落在同一条上 —— **判据不仅要能失败，成功时也要是对的**（`docs/20` §十 的镜像）。
