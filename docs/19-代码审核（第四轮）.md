## 四、新发现

### R1（正确性 · 测试污染生产数据）跑测试会覆盖生产 RAG 索引

`scripts/create_chroma_db.py:95` **无条件**调用
`_build_fts_sidecar(settings.CHROMA_FTS_DB, ...)`，而该函数（`:100-136`）会
`DROP TABLE IF EXISTS chunks` 后重建；`settings.CHROMA_FTS_DB` 的默认值是
**相对路径** `./var/chroma_fts.sqlite`（`settings.py:137`）——即**仓库根的运行时索引**。

而 `tests/test_ingest.py:15` 只隔离了 `db_name`：

```python
def _ingest(corpus, db_name, **kwargs):
    return create_chroma_db.create_chroma_db(str(corpus), db_name=db_name, **kwargs)
```

`create_chroma_db` **没有** `fts_db` 参数，所以测试语料被写进了生产侧车库。

实测（决定性实验）：

| 步骤 | 观察 |
| --- | --- |
| 跑测试前查 `var/chroma_fts.sqlite` | 来源是 `guide.md` / `notes.txt`，内容是 `Mission first. AcmeTech builds…` —— **测试语料**，`data/` 下的 5 个真实语料一个都不在 |
| 把该文件移走后单跑 `pytest tests/test_ingest.py` | 文件**被重新创建**（24576 字节），内容仍是上述测试语料 |
| 用 `scripts/create_chroma_db.py` 对 `data/` 重建后 | 来源恢复为 `AcmeTech_Employee_Handbook.pdf`(3) + 4 个 `.md`(各 1) |

**影响有三层**：

1. 开发者本地跑完测试，`database_search` 的 FTS 词法路就再也检不到真实手册，
   取而代之的是 `guide.md`/`notes.txt`；向量路（Chroma，走 `tmp_path`）没被污染，
   于是**两路召回的数据源不一致**，RRF 融合结果失去意义。
2. 隔离是**点状**的、不是系统性的：`test_ingest_builds_fts_sidecar` 用 `monkeypatch`
   正确隔离了（`monkeypatch.setattr(ingest.settings, "CHROMA_FTS_DB", fts_db)`），
   但**漏点不止一处** —— `tests/agents/test_hybrid_retrieval.py::test_ingest_stamps_source_hash_and_stable_ids`
   的两次 `create_chroma_db` 调用同样没隔离。后一处是**修复后复跑才暴露的**：
   第一次审核时我按「test_hybrid_retrieval 已隔离」一笔带过，属**漏判**，已在 §9.1 更正。
3. 该文件是**跨进程共享**的可变状态：并发跑两个 pytest 会话时，一方 `DROP TABLE`
   会让另一方的 `_build_fts_sidecar` 撞上 SQLite 写锁，而该函数**没有 try/except**
   （只有 `finally: conn.close()`）→ 异常直接冒泡成测试错误。见 §五 W1。

**修法（两层，本轮都做了）**：

- **点修**：给 `create_chroma_db` 加 `fts_db: str | None = None`，默认取
  `settings.CHROMA_FTS_DB`；`test_ingest.py` 与 `test_hybrid_retrieval.py` 的
  建库调用一律显式传 `tmp_path`。
- **兜底**：`tests/conftest.py` 加 autouse fixture，把 `CHROMA_FTS_DB` 默认指向
  临时目录 —— 以后新增测试即使忘了隔离，也不会碰生产索引。需要断言「默认取
  settings」这条分支的用例可在测试体内再 monkeypatch 覆盖回来。

**验收判据（必须能真的失败）**：新增用例，跑 `test_ingest` 后断言
`settings.CHROMA_FTS_DB` 指向的那个文件**未被创建**；不修则必红（已用
`var/probe_r1_guard.py` 注入旧行为验证过，见 §9.1）。

### R2（正确性 · 静默失效）`HYBRID_RECALL_K` 对向量路无效

`rag/hybrid_retriever.py:85` 调 `_vector_hits(query, recall_k)`，而 `_vector_hits`
（`:54-57`）是：

```python
retriever = load_chroma_db()
return retriever.invoke(query)[:k]
```

`load_chroma_db()` 返回的是**单例 retriever**，其 `search_kwargs` 在构造时就被钉死为
`{"k": settings.RAG_TOP_K}`（`agents/tools.py:268`）。默认值：

| 设置 | 默认 | 位置 |
| --- | --- | --- |
| `RAG_TOP_K` | **5** | `settings.py:135` |
| `HYBRID_RECALL_K` | **20** | `settings.py:139` |

→ `retriever.invoke(query)` **最多只返回 5 条**，`[:20]` 是一个**永不生效的截断**。
设计意图「向量召回 20 + FTS 召回 20，再 RRF 融合」实际退化为「**向量 5 + FTS 20**」。

后果：

1. 两路候选池不对等，RRF 融合的收益被削弱 —— 向量路 rank 只到 5，
   分值是 `1/(60+1..5)`，而 FTS 路到 `1/(60+20)`；**排名靠后的融合结果会系统性偏向 FTS**。
2. `_vector_hits` 的 `k` 参数形同虚设：调用方传任何 `k > 5` 都拿不到更多 ——
   这正是本项目最警惕的「**看着生效、其实不生效**」型静默失效（与 P0-1 的 `index=`
   同型：不报错、有结果、但语义已偏）。
3. **零测试覆盖**：`grep HYBRID_RECALL_K tests/` 无命中，没有任何用例断言它生效。

**修法**：`_vector_hits` 不要复用「按 `RAG_TOP_K` 钉死的 retriever」，改用底层
`vectorstore.similarity_search(query, k=k)`；或把单例 retriever 的 `k` 提到
`max(RAG_TOP_K, HYBRID_RECALL_K)`。

**验收判据**：断言 `len(_vector_hits("q", HYBRID_RECALL_K)) > settings.RAG_TOP_K`
（语料足够时）；不修则必红（现状恒为 5）。

### W1（未完全定性）三路并发跑 pytest 时出现过 32 errors

`docs/18` §十 的复现命令是**顺序**执行的。本轮我在同一时刻启动了三个 pytest

tests/agents/test_hybrid_retrieval.py       2 条

tests/test_sqlite_store.py                  2 条

后续三次尝试**均未复现**（0 errors）：

| 组合 | 结果 |
| --- | --- |
| 单跑离线全量 | 309 passed / **0 errors** |
| 两路并发：离线 + 离线 | 309 / 309，**0 errors** |
| 两路并发：离线 + 联网 | 309 / 312，**0 errors** |

**因此本轮不定性为缺陷**，但相关线索是确凿的：这 32 个用例全部触达

三路并发时窗口更宽，撞锁概率更高 —— 这与「只在三路并发时出现」的观察一致。

**建议**：先修 R1（让测试不再写生产路径），再复跑三路并发确认是否消失；
若仍复现，按「SQLite 写锁 + 无异常保护」方向继续定位。

### W4 `fetch_url` 对相对重定向一律拒绝

`tools.py:155` 取 `resp.headers.get("location")` 后直接交给 `_validate_url_safe`，
而后者要求 `url.startswith(("http://", "https://"))`（`:106`）。
RFC 允许相对 `Location`，站点很常见 —— 这类重定向会被判为「redirect target is not allowed」。
安全上无问题（宁拦勿放），属功能保守，若要改进需按 `urljoin` 补全后再校验。
