## 三、V1 的守卫为什么是恒绿的（N1a）

`tests/service/test_service_lifespan.py:123` 的 `test_lifespan_does_not_touch_var_sqlite` 声称：
「删掉 conftest 里的两条 setattr，本用例必须变红」。**实测不成立。**

`var/audit7/probe_K_guard_blind.py` 在同一注入态下跑两种判据：

```text
### 状态 2：注入（删掉 conftest:53-54 两条 SQLITE 隔离）
   PATHCHECK SQLITE_DB_PATH   = 'var/checkpoints.db'    abs=False   ← 已经指向生产库
   PATHCHECK SQLITE_STORE_PATH= 'var/memory_store.db'   abs=False
   提出守卫（路径判据）: rc=1 :: 1 failed, 1 passed      ← 抓到了
   现守卫（mtime 判据）: rc=0 :: 1 passed, 5 warnings    ← 同一注入态下仍然绿
   生产库 mtime/size 是否变化：{'checkpoints.db': False, 'memory_store.db': False}
```

**根因**：现守卫断言的是「跑完 lifespan 后 `var/*.db` 的 `mtime_ns`/`size` 不变」，
而 SQLite **打开一个已存在且已 setup 的库并不写盘** —— 路径无论是否隔离，断言都为真。
它只能抓到「库不存在→被重建」这一种形态（`docs/21` V1 的决定性实验正是这种形态，所以它当时红了）。

### 修法（一条用例同时守住 N1a 与 N1b）

把判据从「副作用快照」换成**路径结构断言**：

```python
# tests/test_isolation_guard.py（新增）
from pathlib import Path
from core.settings import settings

def test_all_stateful_backends_are_isolated() -> None:
    """生产默认值是相对 CWD 的 `./var/...`；被隔离后必然变成 tmp 下的绝对路径。"""
    offenders = [f"{n}={getattr(settings, n)!r}"
                 for n in ("CHROMA_DIR", "CHROMA_FTS_DB", "SQLITE_DB_PATH", "SQLITE_STORE_PATH")
                 if not Path(getattr(settings, n)).is_absolute()]
    assert not offenders, f"以下后端未被测试隔离，会落在生产 var/ 下：{offenders}"
```

判据可证伪：**今天加进去必红**（`CHROMA_DIR` 仍是 `'./var/chroma_db'`）；
删掉 conftest 任意一条 setattr 也必红。实测见 `verify_guards.py` C 段与 `probe_K`。

## 五、N2：`_is_sensitive` 在 Windows 下可被大小写绕过

`src/agents/code/tools.py:25-35` 的全部比较都是大小写敏感的字符串比较：

```python
if any(p.startswith(prefix) for p in parts for prefix in _SENSITIVE_PART_PREFIXES):  # (".env",)
if any(p in _SENSITIVE_FILE_NAMES for p in parts):                                    # ("id_rsa", ...)
if any(sub in p for p in parts for sub in _SENSITIVE_NAME_SUBSTRINGS):                # ("service-account",)
return any(rel.endswith(sfx) for sfx in _SENSITIVE_SUFFIXES)                          # (".pem", ...)
```

而 `read_file` 的守卫检查的是**用户给的字符串**（`:179-181`），真正读取的是
`(root / path).resolve()`（`:182`）——**Windows 的文件系统解析不区分大小写**，
于是「检查的名字」与「读到的文件」不是同一个字符串，守卫被绕过。

**实测（`var/audit7/probe_H_is_sensitive.py`，真实临时 git 仓库）**：

| 调用 | 结果 |
| --- | --- |
| `read_file(".env")` | 被拦 ✅ |
| `read_file(".env.local")` | 被拦 ✅ |
| `read_file("keys/id_rsa")` | 被拦 ✅ |
| `read_file(".ENV")` | **放行，返回 `AUTH_SECRET=real-secret-value`** ❌ |
| `read_file("PRIVATECREDENTIALS/k.txt")` | **放行，返回私钥材料** ❌ |
| `read_file("cert/server.PEM")` | **放行，返回证书正文** ❌ |
| `read_file("svc/SERVICE-ACCOUNT.JSON")` | **放行，读到真实文件** ❌ |

**为什么这条会被长期漏掉**：CI 跑 Linux。Linux 上 `.ENV` 不存在，
`read_file(".ENV")` 会返回 `error: not a file inside the repository: .ENV`
—— **任何写成 `assert out.startswith("error")` 的用例在 CI 上都恒绿**。
守卫必须断言 `"sensitive" in out`，才既能在 Windows 抓真缺陷，又不会在 Linux 假绿。

### 修法（已模拟验证）

全部比较改成 `casefold`：

```python
def _is_sensitive(rel: str) -> bool:
    parts = [p.casefold() for p in rel.split("/") if p not in ("", ".")]
    if any(p in _SENSITIVE_PARTS for p in parts): ...          # 常量本身已是小写
    if any(rel.casefold().endswith(sfx) for sfx in _SENSITIVE_SUFFIXES): ...
```

`probe_H` §3 用同一组 12 个样例跑修法版本 → **12/12 通过**（含 `.ENV`、`.Env.Local`、
`KEYS/ID_RSA`、`SVC/SERVICE-ACCOUNT.JSON`、`CERT/SERVER.PEM`、`.GIT/config`）。

## 六、N3：生产向量库里有 3 条 P0-9 之前的孤儿 chunk

直接查生产库（`var/chroma_db/chroma.sqlite3`）：

| chroma row id | source | source_hash | page |
| --- | --- | --- | --- |
| 1 | ./data\AcmeTech_Employee_Handbook.pdf | — | 0 ← 旧 |
| 2 | ./data\AcmeTech_Employee_Handbook.pdf | — | 1 ← 旧 |
| 3 | ./data\AcmeTech_Employee_Handbook.pdf | — | 2 ← 旧 |
| 4 / 5 / 6 | 同文件（本次重建） | c1c286c0f73f | 0 / 1 / 2 |
| 7–10 | 4 个 .md | ✓ | 0 |

`embeddings` = **10** 行，而 FTS 侧车库只有 **7** 行；差的就是 id 1/2/3
（无 `source_hash` = P0-9 之前的 id 方案）。

**根因**：`scripts/create_chroma_db.py:35` 默认 `delete_chroma_db=False`，
写入用 `add_documents(ids=...)`（`:97`）—— 稳定 id 让**同一次 build 幂等**，
但 id 方案一变（旧的是自增序号），旧行就永远留在集合里；而侧车库是
`DROP TABLE` 重建的（`:117`），所以两边条数必然分叉。

**影响**：向量路检索会命中旧版本内容，且 P0-9 的 `source_hash` 对账
**无法发现**这 3 条（它们根本没有该字段）。RAG 的回答可能引到过期手册文本。

### 修法

建库末尾按本次 build 的 id 集合做一次对账删除（`collection.delete(ids=[...])`
或 `delete_chroma_db=True` 重建），并加一条用例：**语料换一版后重建，`embeddings`
条数必须等于本次 chunk 数**（今天必红：10 ≠ 7）。

## 七、N9：`git_diff` 的 `ref` 可以让 git 写文件（观察项 → 缺陷）

`docs/20` §六 把这条列为「观察项」并建议「加一个 `--` 即可」。实测：

```text
$ git_diff(repo_path=<tmp repo>, ref='--output=<abs>/pwned.txt')
返回首行: ''
是否被写成文件: True
```

`code/tools.py:115` 把模型可控的 `ref` 直接拼进 `git show`：
`["show", "--format=...", "--date=short", ref]`。`--output=<path>` 被 git 当选项，**文件真的被创建**。

**加 `--` 不解决**：`git show <ref> --` 里 `ref` 仍在 `--` 之前，照样按选项解析。
正确修法是**校验 ref**（拒绝以 `-` 开头 / 限制字符集），并同时把
`docs/13:19` 的「固定 git 参数防注入」这句改成如实描述。
