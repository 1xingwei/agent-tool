## 四、新发现

每条都给出「能失败」的判据；探针源码在 `var/audit5/`，可复跑。

### F1（P1 · 可用性）守卫自身故障 = 全部工厂图不可用

`safeguard.py:128-133` 的 `Safeguard.ainvoke` **没有 try/except**：

```python
async def ainvoke(self, messages: list[AnyMessage]) -> SafeguardOutput:
    if self.model is None:
        return SafeguardOutput(safety_assessment=SafetyAssessment.SAFE)
    compiled_messages = self._compile_messages(messages)
    result = await self.model.ainvoke(compiled_messages)   # ← 抛了就冒出去
    return parse_safeguard_output(str(result.content))
```

而 `guard_input` 是**每一个走工厂的 agent 的入口节点**（`graph_factory.py:138`、`:144`）。
`var/audit5/probe_B_safeguard_fatal.py` 把模型打桩成「调用即抛 402 → 余额不足」：

```text
1) 直接调 Safeguard.ainvoke：        ❌ 抛出 RuntimeError: 402 - Insufficient Balance（未兜底）
2) 调图入口节点 safeguard_input：     ❌ 节点抛出 RuntimeError → 整张图的 ainvoke/astream 失败
3) 端到端：真建一张工厂图，ainvoke：   ❌ graph.ainvoke 抛出 RuntimeError
```

**这条不是理论风险。** `probe_F`-adjacent 实测本机配置：

```text
DEEPSEEK_API_KEY 已配置 : True
GROQ_API_KEY 已配置     : False
Safeguard.model is None : False     ← 每个请求都会真调一次 DeepSeek
```

而本项目**已经真实撞过 402**（`docs/18` K1：DeepSeek 余额耗尽导致联网用例 2 failed）。
也就是说：余额耗尽 / 429 / 5xx / 网络抖动时，**所有走工厂的 agent 全线 500**，
错误信息在 `/stream` 上只是一条 `Internal server error`。

三处内部不一致让这更像缺陷而非取舍：

1. **枚举值已经预留了这条路**：`SafetyAssessment.ERROR` 存在，`check_safety`（`graph_factory.py:85-91`）
   已经把 `ERROR` 归到 `safe` 分支 —— 类型系统设计者想过「守卫失败」这件事，只是没接线。
2. **同仓有两处相反的先例**：`core/distill.py` 写了明确的「不致命原则」（摘要失败只 warning）；
   `code_reviewer.recall_reviews` 的记忆读失败也有 try/except。**偏偏守卫最脆。**
3. **无 key 时是 fail-open**（返回 SAFE），有 key 但调用失败时却是硬失败 —— 两种失败模式的
   安全姿态不一致，且没有任何文档记录这个取舍。

**修法（二选一，但必须选一个并写进文档）**：

- **A（推荐，与 distill 一致）**：`try/except Exception` → `logger.warning` + 返回
  `SafeguardOutput(safety_assessment=SafetyAssessment.ERROR)`。`check_safety` 已把它当 `safe`，
  即「守卫不可用 → 放行但留痕」，与本机无 key 时的既有行为一致。
- **B（fail-closed）**：捕获后返回一条固定拒答消息并终止图。安全性更强，但会因守卫的
  第三方故障把所有对话变成拒答 —— 必须显式记入 `docs/11` 并给出运维开关。

**验收判据**：`var/audit5/probe_B_safeguard_fatal.py` 第 2/3 步从「❌ 抛出」变为「✅ 已兜底」。

### F2（P2 · 检索正确性 · 静默失效）FTS 词法路对中文查询与常见查询写法双双失效

`scripts/create_chroma_db.py:118` 用 FTS5 的**默认分词器**建表：

```python
conn.execute("CREATE VIRTUAL TABLE chunks USING fts5(chunk_id, source, page, content)")
```

默认分词器是 `unicode61`：**CJK 连续汉字被当成一个整 token**，不做词级切分。
实测（`var/audit5/probe_C_fts_silent.py`，全部在副本上跑，不碰生产索引）：

```text
=== 生产索引（AcmeTech 英文手册，7 chunk）上的中英查询对比 ===
  'mission'          → ok: 1   [命中]
  'handbook policy'  → ok: 1   [命中]
  '公司的使命和价值观' → ok: 0   [空]
  '年假政策'          → ok: 0   [空]

=== 合成中文语料：文档含「年假政策为每年十五天，需提前申请」===
  '年假政策'            → 0     ← 子串/词级完全检不到
  '年假政策为每年十五天'  → 1     ← 必须整段一模一样才命中
  '十五天'             → 0
```

**第二处更隐蔽：`MATCH` 直接吃原始用户串**（`hybrid_retriever.py:33-37`）：

```text
'what is the "policy'  → ❌ OperationalError: unterminated string
'handbook-policy'      → ❌ OperationalError: no such column: policy
'policy AND'           → ❌ OperationalError: fts5: syntax error near ""
'mission OR'           → ❌ OperationalError: fts5: syntax error near ""
'* draft'              → ❌ OperationalError: unknown special query: draft
```

这些是**完全正常的用户提问**（连字符词、引号、自然语言里的 and/or）。异常被
`except sqlite3.Error` 捕获后返回 `[]`，而 `hybrid_search:97` 是：

```python
if not fts:
    return vector[:top_k]        # 连一条 warning 都没有
```

**后果**：这一层「词法精确召回」（版本号、专有名词、数字 —— 也就是 P0-8 上线的**唯一理由**）
在中文场景下**从未生效过**，而用户、调用方、运维三方都无感。这正是本项目最警惕的那类
「看着生效、其实不生效」的静默失效（与 P0-1 的 `index=`、R2 的 `[:k]` 同型）。

**测试为什么没抓到**：`tests/agents/test_hybrid_retrieval.py` 有 9 条用例，其中
`test_hybrid_search_merges_when_sidecar_present` 用 `_doc("keyword", "v1")` 手工造库，
**查询串是 `"keyword"` 这种干净单词** —— 既不是中文，也不含任何 FTS5 元字符。缝在这里。

**修法（分两层，建议都做）**：

- **查询侧（无脑该做，无副作用）**：进 `MATCH` 之前把查询串规范化 ——
  按非字母数字切分、丢弃 FTS5 操作符（`AND/OR/NOT/NEAR`）、每个 token 加双引号后
  用 `OR` 连接（如 `"handbook" OR "policy"`）。这同时消灭 F2 的语法错与
  `handbook-policy` 这类连字符查询。
- **建表侧（要重建索引）**：`tokenize='trigram'` 能让中文子串命中（代价是索引体积变大），
  或引入 CJK 分词器。这是**产品决策**，不能顺手改 —— 需要重跑 `create_chroma_db.py`。
- **可观测性（最便宜的一条）**：把 `_fts_hits` 的失败从 `logger.debug` 提到 `warning`，
  并让 `hybrid_search` 在「FTS 有库但 0 命中」时打一条 warning。现在连调试都要开 DEBUG 才看得到。

**验收判据**：新增用例断言「含引号/连字符/中文的查询不会抛 OperationalError
且能命中同形 token」，以及「FTS 侧车存在但 0 命中时产生 warning」。

### F3（P2 · 数据面）代码审查 agent 的文件工具没有敏感路径清单

`agents/code/tools.py` 的 `file_search` / `read_file` 只做了**路径穿越**防护
（`read_file:150-154` 的 `..` 判定 + `is_relative_to(root)`），**没有敏感文件拒绝清单**。
`file_search` 只跳过 `.git/.venv/__pycache__/node_modules`（`:116`），
`.env` 与 `privatecredentials/` 不在其中；`read_file` 连这个跳过列表都没有。

实测（`probe_D_misc.py` 的 D5，只打印键名不打印键值）：

```text
file_search(content_pattern='AUTH_SECRET') 命中：
  .env:AUTH_SECRET
  .env.example:AUTH_SECRET
  docs/01-架构说明.md:...
read_file('.env') 返回 2791 字符          ← 本机 .env 里的真实密钥全文
privatecredentials/ 可枚举 → 'privatecredentials/.gitkeep'
```

**影响**：`code-reviewer` 的指令是「read the repository」，工具输出直接进提示词 → 出网到
DeepSeek。一次「帮我审查这个仓库的安全配置」就可能把 `.env` 全文送出去。
`.gitignore` 的忽略规则对这两个工具完全无效。

**修法**：加一个模块级 denylist（`.env*`、`privatecredentials/**`、`*.pem`、`*.key`、
`id_rsa*`、`.git/**`、`*.sqlite`），在 `read_file` 与 `file_search` 两处都拦；
**两条路径都要拦**（这正是上轮 R1 的教训：只在 `test_ingest` 修、漏了 `test_hybrid_retrieval`）。

**验收判据**：新增用例断言 `read_file(".env")` 被拒、`file_search(content_pattern="AUTH_SECRET")`
在 `.env` 上无命中；反例注入（把拦截删掉）必须变红。

### F4（P2 · 启动健壮性）`lifespan` 里 `get_agent()` 落在 `try` 之外

`service.py:125-137`：

```python
for a in agents:
    try:
        await load_agent(a.key)
        logger.info(f"Agent loaded: {a.key}")
    except Exception as e:
        logger.error(f"Failed to load agent {a.key}: {e}")
        # 继续处理其他 agent，而非让启动失败      ← 注释的承诺
    agent = get_agent(a.key)                      # ← :133 在 try 之外
    agent.checkpointer = saver
```

`get_agent` 对**未加载**的 `LazyLoadingAgent` 会抛 `RuntimeError`（`agents.py:97`，这是上轮
W2 刚写清楚的语义）。所以「load 失败 → 记 error 继续」这条路径根本走不完：
紧接着的 `get_agent` 必然再抛，且没有任何兜底 → 整个 lifespan 失败 → **服务起不来**。

`var/audit5/probe_A_lifespan_isolated.py` 只让 `github-mcp-agent` 一个 agent 加载失败：

```text
Failed to load agent github-mcp-agent: MCP 服务器不可达（模拟凭证失效 / 网络失败）
Error during database/store/agents initialization: Agent github-mcp-agent not loaded. Call load() first.
❌ 启动整体失败：RuntimeError: Agent github-mcp-agent not loaded. Call load() first.
```

**如实说明可达性**：今天这条路径**打不到** —— 唯一的 `LazyLoadingAgent`
（`GitHubMCPAgent.load`，`github_mcp_agent.py:80-87`）自己 `except Exception` 吞掉了一切并
置 `_loaded = True`。所以它是**潜在缺陷**，与 F1 的「已经能撞到」不同级。
但代价只有 3 行，而它保护的是「服务能不能起来」：一旦有人加第二个懒加载 agent、
或给 `GitHubMCPAgent.load` 加上重抛，故障模式就是全站不可用而非单 agent 不可用。

**修法**：把 `get_agent(a.key)` 挪进 `try`，失败则 `continue`；
或改为 `agent = get_agent(a.key) if ... else None` 并跳过未加载者。
**验收判据**：`probe_A_lifespan_isolated.py` 从「❌ 启动整体失败」变为「✅ 存活」。

### F5（P3 · 一致性）同一事实在两条 HTTP 路径上是两种语义

| 路径 | 代码 | 实测（`agent 未加载`） |
| --- | --- | --- |
| `POST /{agent_id}/invoke` | `service.service._resolve_agent:79-98`（**只**映射 `KeyError`） | `RuntimeError` 冒出 → **500** |
| `POST /agui/{agent_id}/run` | `service/agui.py:104-106`（`except (KeyError, RuntimeError)`） | `HTTPException` → **404** |

`_resolve_agent` 的 docstring 特意论证过：`RuntimeError` 表示「服务器状态 bug，不该伪装成 404」。
`agui.py` 把同一件事说成了「agent 不存在」。两者都没错到崩溃，但**同仓对同一事实给了两种答案**，
排查时会误导（404 = 客户端拼错了 id；500 = 服务端坏了，处理方式完全不同）。

**修法**：`agui.py` 只接 `KeyError` → 404，`RuntimeError` 继续 500。
（`agui` 不能 import `service.service` —— 会成环，所以只能各自维护一份判定，
但至少要保证**判定一致**，并加一条用例把两者钉住。）

**验收判据**：新增用例同时断言两条路径对「未加载 agent」的状态码（404 / 500），
将来任一侧改动都会变红。

### F6（P3 · 客户端）未知 SSE 事件类型被当成「流结束」

`client.py:233-246` 的 `match parsed["type"]` **没有 default 分支** → 返回 `None`；
而调用方 `client.py:322-324`：

```python
parsed = self._parse_stream_line(line)
if parsed is None:
    break          # ← "[DONE]" 与「不认识的类型」走同一个分支
```

实测（`probe_D_misc.py` D4，用假 SSE 流喂给真 `AgentClient.astream`）：

```text
服务端发了 3 个有效事件（token A / 未来新增的 heartbeat / token B），客户端只拿到 ['A']
```

服务端加一种事件类型（AG-UI 已经在用 `RAW`/`CUSTOM` 等更多类型）就会静默砍掉客户端
后续的全部输出，且不报错。**修法**：未知类型 `continue` 而不是返回 `None`，
让 `None` 只表示 `[DONE]`。

**验收判据**：喂一条含未知类型的三段流，断言拿到 `['A', 'B']`。

### F7（P3 · 持久化）`remember_review` 的写路径没有兜底，读路径有

实测（`probe_D_misc.py` D3，store 打桩成写即抛 `database is locked`）：

```text
remember_review → ❌ RuntimeError: database is locked（写失败拖垮整次运行）
recall_reviews  → ✅ 已兜底，返回 {'recalled_reviews': '', 'messages': []}
```

`recall_reviews`（`code_reviewer.py:90-95`）有注释「记忆读失败不应影响本次审查」，
`remember_review`（`:128`）的 `await store.aput(...)` 却裸奔 —— 而它是 `done_node`，
**在整张图跑完之后**抛出。后果最刺眼的一种：模型已经生成好完整回答，用户却什么都没拿到。
**修法**：与读路径对称地 try/except + warning。**验收判据**：上面第 1 行变为「✅ 已兜底」。

### F8（P3 · 可观测性）`command_agent` 的 `print` 仍在生产 stdout

上一轮修掉了 `Safeguard` 每请求 `print()`，但没顺手把同类清干净：

```text
一次 ainvoke 往 stdout 写了 2 行：['Called A', 'Called C']
```

`command_agent.py:20/39/44` 的 `print("Called A/B/C")` 是教学样例留下的调试输出，
每次请求都往服务器 stdout 写。**修法**：`logger.debug` 或直接删。
**验收判据**：新增用例用 `capsys` 断言一次 `ainvoke` 后 stdout 为空。

### F9（文档 · 声实不符）`docs/09:69` 对本机 Safeguard 路径的判断已经失效

```text
docs/09:69  | `guard_input` | graph_factory.py:69 | Safeguard().ainvoke(messages) → safety |
             **可选**：`GROQ_API_KEY` 为空时 `Safeguard.model=None` 并直接返回 `SAFE`
```

## 十、方法论备忘（本轮我自己犯的一次「假的红」）

`probe_E_invoke_streammode.py` 第一次跑出的是**错误的分类结论**：它把注册表里 11 张图
全判成「`@entrypoint` → Pregel」，只留下 1 张 `LazyLoadingAgent`。原因是我把
`isinstance(gl, Pregel)` 写在了 `isinstance(gl, CompiledStateGraph)` **前面** ——
而 `CompiledStateGraph` 是 `Pregel` 的子类，先判父类会把所有子类吞进去。

修法是交换判断顺序，修完输出变成「1 张 Pregel + 9 张 CompiledStateGraph（含 2 张 supervisor）+
1 张懒加载」，与 `agents.py` 的注册表逐项对得上。

**记下来的原因**：这就是本项目反复强调的「判据要能真的失败」的镜像版本 ——
**判据不仅要能失败，还要在它成功的时候是对的**。如果我没做这次交叉核对，
报告里就会多一条「11 张图构造方式判错了」的假发现，而它看起来和真发现一模一样。
凡是用 `isinstance` 做类型分派的地方（本项目还有 `agents.py:95`、`memory/__init__.py`
的分支），判断顺序都值得多看一眼。
